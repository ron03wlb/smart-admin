## 1. Three Data Paths

平台數據在時效性與準確性之間取得平衡，採三路數據路徑設計。

| 路徑 | 延遲 | 準確性 | 用途 |
|------|------|--------|------|
| **Hot Path** (即時) | <= 5 秒 | 95% | 即時監控儀表板 |
| **Warm Path** (近即時) | 5-60 秒 | 98% | 營運報表 |
| **Cold Path** (批次) | T+1 | 100% | 財務、合規報告 |

**設計原則**: Hot Path 優先可用性 (AP)，容許短暫不一致；Cold Path 優先一致性，確保財務/合規報表 100% 準確。

## 6. PII Masking Before Analytics

**規則**: PII 在進入分析層之前**必須完成脫敏**。報表中不得出現原始 PII。

| 欄位 | 脫敏方式 | 範例 |
|------|---------|------|
| 姓名 | 部分遮蔽 | 張**明 |
| 電話 | 中間遮蔽 | 138****5678 |
| 證件號 | 大部分遮蔽 | A1****89 |
| Email | 部分遮蔽 | r**@gmail.com |

## 8. Report Data Correction Flow

| 步驟 | 說明 | 負責人 |
|------|------|--------|
| 1 | 發現數據異常 (自動偵測或人工發現) | 系統 / BI 團隊 |
| 2 | 建立修正工單 + 影響範圍評估 | BI 團隊 |
| 3 | 追溯修正 (重跑 ETL Pipeline 或手動調整) | BI 工程師 |
| 4 | 修正後報表標記「已修正」+ 修正時間 | 系統 |
| 5 | 合規報表修正須 **CFO 審批** | CFO |
| 6 | 已對外發布的合規報表修正須**通知監管機構** | 合規經理 |

**規則**: 修正記錄保留原始值與修正值，**不可覆蓋原始數據** (審計要求)。

## 9. Regulatory Report Impact Assessment

> v2.2 新增 — GAP-8 (報表修正對已提交監管報告影響)
> 部分規則待合規團隊確認

### 9.1 Impact Detection Flow

| 步驟 | 動作 | 負責人 |
|------|------|--------|
| 1 | 修正觸發時，系統自動檢查該數據是否包含在已提交的監管報告中 | 系統 |
| 2 | 若涉及已提交報告 -> 自動標記 `REGULATORY_IMPACT` | 系統 |
| 3 | 重要性評估: 修正值 <= 0.1% 報告值 -> 僅記錄; > 0.1% -> 強制通知 | 合規經理 |
| 4 | 生成正式修正通知 (原始值 vs 修正值 + 影響說明) | 系統 + 合規經理 |
| 5 | 重大修正須在 **5 個工作日內**通知監管機構 | 合規經理 |
| 6 | 完整審計鏈: 原始報告 -> 修正觸發 -> 修正報告 -> 監管通知 | 系統 |

### 9.2 Materiality Thresholds

> 部分待合規確認具體閾值

| 修正類型 | 閾值 | 動作 |
|---------|------|------|
| GGR/NGR 修正 | > 0.1% | 通知監管機構 |
| 玩家數修正 | > 1% | 通知監管機構 |
| AML/SAR 相關修正 | **零閾值** | 一律通知 |

## 10. Compliance Report Automation Levels

| 報表 | 自動化等級 | 說明 | 人工介入 |
|------|----------|------|---------|
| GGR/NGR 日報 | **全自動** | 系統自動計算 + 生成 + 歸檔 | 僅異常時審查 |
| GDPR 刪除統計 | **全自動** | 自動追蹤刪除請求生命週期 + 月度統計 | 僅年度審計時審查 |
| AML/KYC 月度指標 | **全自動** | 自動計算各指標 + 生成趨勢報告 | 僅異常閾值觸發審查 |
| MGA 月度監管報表 | **半自動** | 系統自動填充數據，合規經理審核後提交 | 審核 + 簽章 + 提交 |
| UKGC SAR 統計 | **半自動** | 系統自動彙總 SAR 數據，MLRO 審核 | MLRO 審核 + 提交 |
| 負責任博彩月報 | **半自動** | 自動彙總自我排除、限額數據 | 合規經理審核 + 提交 |
| 稅務報表 | **半自動** | 系統計算稅基，CFO 審核後提交 | CFO 審核 + 會計師簽章 |
| 年度 PCI-DSS 合規報告 | **手動** | QSA 第三方稽核，系統提供數據匯出 | 全程手動配合稽核 |

**自動化等級定義**:
- **全自動**: 系統端到端完成，無需人工介入。異常時自動告警。
- **半自動**: 系統產生初版，需指定人員審核後提交。
- **手動**: 需人工主導，系統僅提供數據支持。

## 13. DR Three-Tier System (SSOT)

> **SSOT**: 本段為 DR 三級體系的權威定義 (Ch10 S10.4)。

| 層級 | 適用系統 | RPO | RTO | 備註 |
|------|---------|-----|-----|------|
| **Tier 1** | 支付/錢包 | < 5 分鐘 (近零) | < 15 分鐘 | 資金安全最高優先 |
| **Tier 2** | 玩家服務/遊戲 | < 1 小時 | < 4 小時 | 客戶體驗 |
| **Tier 3** | 分析/報表 | < 24 小時 | < 24 小時 | 可容忍延遲 |

### 13.1 DR Drill Schedule

| 季度 | 演練範圍 | 演練類型 | 驗證標準 |
|------|---------|---------|---------|
| **Q1** | Tier 1 (支付/錢包) | 完整 Failover | RTO < 15 分鐘 + 餘額一致性 100% + 零交易遺失 |
| **Q2** | Tier 1 + Tier 2 (玩家/遊戲) | 完整 Failover | T1 + 玩家服務 RTO < 4h + Session 恢復率 > 99% |
| **Q3** | Tier 1 (支付/錢包) | 桌面推演 + 部分 Failover | 操作手冊完整性驗證 + 新團隊成員參與 |
| **Q4** | 全系統 (T1+T2+T3) | 完整 Failover | 年度全系統驗證，含報表恢復、合規數據完整性 |

### 13.2 DR Verification Checklist

每次演練必驗:

| 驗證項目 | 通過標準 |
|---------|---------|
| RTO 達成 | 各 Tier 恢復時間 <= 目標值 |
| RPO 達成 | 數據遺失量 <= 目標值 |
| 餘額一致性 | 恢復後錢包餘額與備份一致 (差異 = 0) |
| 交易連續性 | 恢復後所有 in-flight 交易有明確狀態 (成功/回滾) |
| 外部服務重連 | PSP、GP 連線在 RTO 內恢復 |
| 監控恢復 | 告警系統、儀表板正常運作 |
| 通知執行 | 相關人員收到通知 (時間戳記錄) |

**演練失敗處置**: 若任何 Tier 1 驗證項未通過，須在 **2 週內**安排補充演練，並提交根因分析報告至 CTO。

## 19. CAP Theorem Trade-Offs

| 系統 | 策略 | 說明 |
|------|------|------|
| **錢包 / 支付** | **CP** (一致性優先) | 資金操作不容許不一致，分區時拒絕寫入並回傳錯誤 |
| **遊戲大廳 / CMS** | **AP** (可用性優先) | 允許短暫的數據不一致 (如遊戲列表延遲更新)，確保玩家可瀏覽 |
| **風控引擎** | **CP** (一致性優先) | 規則評估需準確，分區時寧可延遲也不漏判 |
| **報表 / 分析** | **AP** (可用性優先) | 最終一致性即可，允許短暫延遲 |
| **客服系統** | **AP** (可用性優先) | 玩家能聯繫客服比即時數據一致更重要 |
