# 第 16 章：事件回應與營運韌性

---

## 16.1 模組概述

事件回應模組定義平台在發生服務中斷、安全事件、資料洩露等異常情況時的標準化處理流程。作為 24/7 金融服務平台，必須具備快速回應、有效溝通、系統復原的能力。

**核心職責**: 事件分級、升級路徑、War Room 機制、溝通模板、事後檢討、營運韌性演練

---

## 16.2 事件嚴重度分級

| 等級 | 名稱 | 定義 | 範例 | 回應 SLA |
|------|------|------|------|---------|
| **P0** | 嚴重 (Critical) | 核心服務完全中斷，影響所有/大部分用戶 | 平台全面宕機、支付系統癱瘓、大規模資料洩露 | < 15 分鐘 |
| **P1** | 高 (High) | 核心功能嚴重降級，影響大量用戶 | 單一 PSP 故障、遊戲大廳部分不可用、風控系統延遲 | < 30 分鐘 |
| **P2** | 中 (Medium) | 非核心功能異常，影響部分用戶 | 報表延遲、單一遊戲 RTP 異常、客服系統緩慢 | < 2 小時 |
| **P3** | 低 (Low) | 次要功能異常，影響少量用戶 | UI 顯示錯誤、非關鍵通知延遲 | < 8 小時 |
| **P4** | 資訊 (Info) | 潛在問題或改善機會 | 效能基準偏移、非緊急安全更新 | 下一個工作日 |

### 核心服務定義

| 服務 | 分類 |
|------|------|
| 錢包系統 (Ch2) | 核心 |
| 支付系統 (Ch3) | 核心 |
| 遊戲整合 (Ch4) | 核心 |
| 風控系統 (Ch6) | 核心 |
| 玩家認證/登入 | 核心 |
| 負責任博彩 (Ch15) | 核心（合規要求） |
| 促銷系統 (Ch5) | 重要 |
| 客服系統 (Ch12) | 重要 |
| 報表系統 (Ch9) | 次要 |
| 代理門戶 (Ch8) | 次要 |

## 16.3 升級矩陣

### 通知對象

| 等級 | 即時通知 | 15 分鐘內通知 | 30 分鐘內通知 |
|------|---------|-------------|-------------|

### 通知管道

## 16.4 War Room 機制

### 啟動條件

| 條件 | 動作 |
|------|------|
| P0 事件確認 | **強制**啟動 War Room |
| P1 事件持續 > 30 分鐘 | 啟動 War Room |
| P2 事件升級 | 視情況啟動 |

### War Room 角色

| 角色 | 職責 | 備註 |
|------|------|------|
| **事件指揮官 (IC)** | 整體協調、決策、時間線管理 | SRE Lead 或 On-Call Manager |
| **技術負責人 (TL)** | 技術診斷與修復 | 相關模組 Tech Lead |
| **溝通負責人 (CL)** | 內部/外部溝通、狀態更新 | PM 或 CS Lead |
| **記錄員** | 記錄時間線、決策、行動項 | 輪值 |

### War Room 規則

- 每 15 分鐘更新一次狀態（P0）/ 每 30 分鐘（P1）
- 所有決策記錄在事件時間線中
- IC 有權動員任何團隊成員
- War Room 持續到事件降級或解決

## 16.5 溝通模板

### 內部溝通

**事件宣告模板**:
```
[P{等級}] {服務名稱} — {簡述}
影響: {影響範圍}
開始時間: {時間}
IC: {姓名}
War Room: {連結}
下次更新: {時間}
```

### 玩家溝通

| 事件類型 | 溝通管道 | 訊息範例 |
|---------|---------|---------|
| 平台維護 | 公告橫幅 + Push | 「平台正在進行緊急維護，預計 {時間} 恢復。您的資金安全不受影響。」 |
| 支付延遲 | 公告橫幅 + Email | 「部分出金處理暫時延遲，我們正在積極處理。已提交的出金將照常執行。」 |
| 遊戲不可用 | 遊戲大廳提示 | 「部分遊戲暫時不可用，請嘗試其他遊戲。」 |

### 監管溝通

| 條件 | 通知時限 | 通知對象 |
|------|---------|---------|
| 玩家資料洩露 | 72 小時內 (GDPR) / 24 小時內 (UKGC) | 資料保護機構 + 監管機構 |
| 大規模服務中斷 (> 4 小時) | 24 小時內 | 適用牌照監管機構 |
| 資金安全事件 | 即時 | CFO + 監管機構 |

## 16.6 事後檢討 (Post-Mortem)

### 強制性

| 事件等級 | 事後檢討要求 |
|---------|-------------|
| P0 | **強制** — 5 個工作日內完成 |
| P1 | **強制** — 10 個工作日內完成 |
| P2 | 建議 — 若有學習價值 |
| P3/P4 | 選擇性 |

### 檢討報告結構

| 章節 | 內容 |
|------|------|
| 概要 | 事件類型、影響範圍、持續時間、MTTR |
| 時間線 | 完整事件時間線（偵測 → 回應 → 修復 → 驗證） |
| 根本原因 | 5-Why 分析或魚骨圖 |
| 影響評估 | 受影響玩家數、財務影響、合規影響 |
| 行動項 | 預防重複發生的具體措施 + 負責人 + 截止日 |
| 學習 | 做得好的 + 可改進的 |

### 無責文化

- 事後檢討聚焦於系統與流程，**不追究個人責任**
- 目標: 從事件中學習，改善系統韌性
- 所有檢討報告公開於內部知識庫

## 16.7 營運韌性演練

### 演練類型

| 類型 | 頻率 | 範圍 | 說明 |
|------|------|------|------|
| **桌面演練** | 每月 | 團隊 | 模擬事件情境，演練升級流程 |
| **故障注入** | 每季 | 系統 | Chaos Engineering（如隨機關閉服務節點） |
| **完整 DR 演練** | 每半年 | 全平台 | 模擬主資料中心故障，切換至 DR 站點 |
| **滲透測試** | 每年 | 安全 | 第三方滲透測試 + 修復 |

### DR 演練目標

| 指標 | 目標 |
|------|------|
| RTO 達成率 | 100%（在演練中驗證） |
| RPO 達成率 | 100%（資料損失 = 0） |
| 演練到實際切換時間 | < 目標 RTO 的 80% |

## 16.8 Runbook 維護

### 要求

| 項目 | 規則 |
|------|------|
| 覆蓋率 | 每個核心服務至少 1 份 Runbook |
| 更新頻率 | 每季度審閱 + 每次事後檢討後更新 |
| 格式 | 標準化模板（症狀 → 診斷 → 修復步驟 → 驗證） |
| 可及性 | 所有 On-Call 人員可在 < 30 秒內存取 |
| 版本控制 | Git 管理，變更需 Peer Review |

## 16.9 KPI

| KPI | 目標 | 說明 |
|-----|------|------|
| P0 MTTD (平均偵測時間) | < 5 分鐘 | 從異常發生到告警觸發 |
| P0 MTTR (平均修復時間) | < 1 小時 | 從偵測到服務恢復 |
| P1 MTTR | < 2 小時 | — |
| P0 事後檢討完成率 | 100% | 5 個工作日內 |
| P0/P1 重複事件率 | < 5% | 同類事件 90 天內不再發生 |
| DR 演練成功率 | 100% | 每次演練達成 RTO/RPO 目標 |
| Runbook 覆蓋率 | 100% | 核心服務 |

---

## 16.10 成功指標

| 指標 | 目標 | 說明 |
|------|------|------|
| 年度 P0 事件數 | < 4 次 | 平均每季不超過 1 次 |
| P0 玩家影響時間 | < 4 小時/年 | 累計 |
| 事件溝通滿意度 | ≥ 4.0/5 | 內部調查 |
| 行動項完成率 | ≥ 95% | 事後檢討行動項在期限內完成 |
