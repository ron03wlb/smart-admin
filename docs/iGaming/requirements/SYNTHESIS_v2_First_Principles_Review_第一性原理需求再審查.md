## 三、新發現：v1 遺漏的觀點 (第一性原理補充)

以下為本次深度審查新發現、v1 未覆蓋的缺漏。按第一性原理五問分類。

### 3.1 錢怎麼流動？— 新增 3 項

#### NF-01：BONUS 錢包負餘額保護缺失 — HIGH

**發現**: Ch2 §2.3 定義 CASH 錢包有 5 秒負餘額容忍窗口 (H-01 已修復)，但 BONUS 錢包未定義類似機制。若促銷系統發放紅利的同時，GP 回調 Debit 正在扣款 BONUS 餘額，存在短暫超扣風險。

**證據**: BONUS 錢包的並發場景包括: (1) 流水計算引擎正在扣除已完成部分; (2) GP 回調正在使用 BONUS 資金投注; (3) 紅利過期定時任務正在沒收。三者同時發生時，BONUS 餘額可能短暫為負。

**建議**: Ch2 新增 BONUS 錢包並發控制: 與 CASH 相同的樂觀鎖機制，BONUS 餘額不允許為負 (不同於 CASH 的 5 秒容忍)，扣除操作前須先鎖定再檢查。

**優先級**: P1 (Phase 2)
**信心度**: 中 — 需技術團隊確認 BONUS 錢包是否共用 CASH 的並發控制機制

---

#### NF-02：返水計算視窗與時區交界問題 — MEDIUM

**發現**: Ch5 §5.6 定義返水「每日/每週計算」，但未定義計算視窗的時區基準。Ch10 §10.10 規定 UTC 存儲，但返水計算是按「玩家當地日」還是「平台 UTC 日」？

**證據**: 一個 UTC+8 的玩家在 UTC 日切 (北京時間早上 8 點) 前後的投注，可能被分配到不同的返水計算週期。若兩個週期的投注額各自未達返水門檻但合計超過，玩家將損失返水。

**建議**: Ch5 §5.6 明確: 返水計算視窗以**租戶配置時區** (param_key: `tenant.timezone`) 為準，每日 00:00:00–23:59:59 (租戶時區)。跨時區的品牌各自計算。

**優先級**: P2

---

#### NF-03：加密貨幣確認期間雙花防護 — HIGH

**發現**: Ch3 提到加密存款需 AML 審查，C-05 已解決「存款時轉換」策略。但未定義**區塊鏈確認數不足時**的雙花 (Double Spend) 防護。BTC 1 次確認即入帳 vs 6 次確認才安全之間的平衡點未明確。

**證據**: Heptabase 風控研究指出加密支付是新興風險向量。行業標準: BTC ≥ 3 確認 / ETH ≥ 12 確認 / USDT-TRC20 ≥ 20 確認。過早入帳可能遭遇鏈重組 (Chain Reorg) 導致平台損失。

**建議**: Ch3 新增加密存款確認策略表:

| 幣種 | 最低確認數 | 臨時入帳 | 全額可用 |
|------|----------|---------|---------|
| BTC | 1 | 是 (標記為 pending) | ≥ 3 確認 |
| ETH | 6 | 是 (標記為 pending) | ≥ 12 確認 |
| USDT (TRC20) | 10 | 是 | ≥ 20 確認 |

pending 期間: 可投注但不可提款。確認數可配置 (param_key: `crypto.{coin}.min_confirmations`)。

**優先級**: P1 (Phase 2 — 若支援加密支付)

### 3.2 風險怎麼控制？— 新增 4 項

#### NF-04：風控規則版本回滾的投注追溯影響 — HIGH

**發現**: Ch6 §6.12 定義 Config-Driven 規則治理含 Canary 部署與回滾。但回滾風控規則後，在新規則生效期間已標記的 FLAG/BLOCK 案件如何處理？是維持原決策還是重新評估？

**證據**: 場景: 新規則上線 2 小時後發現誤報率過高 (>10%)，回滾至舊規則。期間 500+ 筆投注被 FLAG。若不重新評估，大量正常玩家被誤判；若重新評估，需回溯處理引擎的計算能力和審計追蹤。

**建議**: Ch6 §6.12 新增「規則回滾後處理策略」:
1. 回滾時自動標記受影響時間窗口
2. 已 FLAG 但未人工處理的案件 → 自動重新評估 (以回滾後規則)
3. 已人工處理 (APPROVED/REJECTED) 的案件 → 維持人工決策 (不回滾)
4. 已執行自動 BLOCK 的案件 → 自動標記為「需複查」，24h SLA

**優先級**: P1
**信心度**: 高 — 直接影響風控品質和玩家體驗

---

#### NF-05：跨品牌玩家身份關聯偵測 — HIGH

**發現**: Ch6 定義多帳號偵測，Ch7 定義多租戶隔離。但未明確: 同一 Admin 下不同 Brand 的相同玩家 (同一自然人) 是否視為「多帳號」？隔離原則與詐欺偵測存在張力。

**證據**: 一個玩家在 Brand A (歐洲站) 和 Brand B (亞洲站) 各有帳戶。如果兩個品牌共享 Admin，風控系統能否跨品牌查詢？若可以，違反資料隔離原則；若不可以，無法偵測跨品牌套利。

**Heptabase 研究對照**: 風控架構報告強調「全維度」風控，但多租戶設計強調「100% 資料隔離」。兩者在跨品牌場景下矛盾。

**建議**: Ch6 + Ch7 新增「跨品牌風控協作原則」:
1. **預設**: 品牌間資料完全隔離 (合規優先)
2. **例外**: Admin 可啟用「匿名化跨品牌信號共享」— 僅共享風險信號 (高風險 flag、設備指紋 hash)，不共享 PII
3. 匿名化信號由平台層 (Admin) 維護，不可下推至品牌/租戶層
4. GDPR 影響: 需在隱私政策中告知「集團內風控信號共享」

**優先級**: P1 (Phase 3 — 多品牌上線前)

---

#### NF-06：AI/ML 模型治理框架缺失 — MEDIUM

**發現**: N-01 已決策「Phase 3 引入 ML 加權」，Heptabase 研究中有加權聚合模型設計 (規則 60% + ML 40%)。但需求文檔缺少 ML 模型治理框架: 模型訓練數據要求、模型偏差監控、解釋性要求、模型審計。

**證據**: 多個管轄區 (特別是 UKGC) 開始要求 AI 決策的可解釋性。若風控使用 ML 模型自動拒絕玩家提款，玩家有權要求解釋 (GDPR Art. 22)。

**建議**: Phase 3 需求定義中新增 ML 模型治理章節:
1. 模型可解釋性要求 (每個自動決策須提供前 3 個影響因子)
2. 模型公平性監測 (按年齡、性別、國籍分群監控誤報率差異)
3. 模型版本管理與 A/B 測試框架
4. 人工覆核比例要求 (初期 ML 決策 100% 需人工確認)

**優先級**: P2 (Phase 3 準備)

---

#### NF-07：內部威脅 (Insider Threat) 防護不足 — HIGH

**發現**: Ch13 聚焦外部安全威脅 (GDPR、PCI-DSS、加密)，Ch7 定義 RBAC 和 MFA。但缺少「惡意內部人員」場景: 擁有生產環境權限的工程師或客服人員利用權限進行欺詐。

**證據**: iGaming 行業內部威脅案例包括: 客服人員為關聯帳戶手動調整餘額、風控分析師批准關聯帳戶的可疑提款、DBA 直接修改資料庫。Ch7 的 RBAC 防止越權，但不防止合法權限範圍內的濫用。

**建議**: Ch13 新增 §13.X 內部威脅防護:
1. 四眼原則 (Four-Eyes): 所有 >$1K 的手動餘額調整需第二人審批
2. 行為異常偵測: 監控管理員操作模式 (頻率、金額、時間異常)
3. 蜜罐帳戶: 設置測試帳戶監測未授權存取
4. 定期權限審查: 季度 access review，離職即時撤銷

**優先級**: P1

### 3.3 玩家體驗怎麼保障？— 新增 2 項

#### NF-08：多設備同步與 Session 衝突 — MEDIUM

**發現**: Ch11 定義響應式設計和 App 支援，但未定義玩家在多設備同時登入時的行為。一個玩家在手機投注的同時，在桌面發起提款——兩個 Session 的可下注餘額是否即時同步？

**證據**: Ch2 的可下注餘額計算依賴即時鎖定金額。若手機 Session 的投注鎖定未即時反映在桌面 Session，可能出現桌面顯示的餘額允許提款，但實際已被手機 Session 的投注佔用。

**建議**: Ch11 + Ch2 新增多 Session 策略:
1. 餘額更新通過 WebSocket 即時廣播至所有活躍 Session
2. 提款操作前強制刷新餘額 (不依賴客戶端緩存)
3. 可選配置: 高風險帳戶限制單一活躍 Session

**優先級**: P2

---

#### NF-09：無障礙 (Accessibility) 合規缺失 — MEDIUM

**發現**: Ch11 §11.3 提到 Core Web Vitals 但未提及 WCAG 無障礙標準。多個管轄區 (EU、UK、澳洲) 正推動數位無障礙法規，iGaming 平台可能在 2027 年前面臨強制要求。

**建議**: Ch11 新增無障礙基礎要求:
1. WCAG 2.1 AA 級作為基線目標
2. 螢幕閱讀器相容性 (遊戲大廳、餘額顯示、交易歷史)
3. 鍵盤導航完整支援
4. 色彩對比度符合標準

**優先級**: P2 (Phase 3+)

---

### 3.4 多租戶怎麼隔離？— 新增 1 項

#### NF-10：租戶遷移與退出策略 (Tenant Offboarding) — MEDIUM

**發現**: Ch7 定義租戶創建流程和權限，但未定義租戶退出: 當一個品牌決定離開平台時，其玩家數據、交易歷史、合規記錄如何處理？

**證據**: 白標客戶合約通常 12–24 個月，到期後可能遷移至自建平台或競爭對手。需求文檔未定義: (1) 數據匯出格式; (2) 數據刪除 vs 保留的法律義務; (3) 過渡期服務 SLA。

**建議**: Ch7 新增 §7.X 租戶退出策略:
1. 數據匯出: 標準格式 (JSON/CSV)，含玩家資料、交易歷史、合規記錄
2. 保留義務: AML 記錄依法保留 5–7 年 (匿名化)
3. 過渡期: 90 天通知 + 30 天唯讀期 + 數據刪除
4. 資金結算: 退出前所有玩家餘額必須清零或轉出

**優先級**: P2

### 3.5 系統怎麼不倒？— 新增 2 項

#### NF-11：灰度發布 (Canary/Blue-Green) 需求未文檔化 — MEDIUM

**發現**: Technical 文檔提到 Kubernetes 滾動更新，Ch16 事件回應提到事件分級。但需求層面未定義灰度發布策略——尤其是涉及錢包、支付等金融交易的服務，直接滾動更新風險極高。

**建議**: Ch10 新增部署策略需求:
1. 金融核心服務 (錢包、支付、風控): 必須 Canary 部署，5% → 25% → 50% → 100%
2. 非核心服務: 標準 Rolling Update
3. Canary 自動回滾條件: 錯誤率 >1%、延遲 >P99 2x、交易失敗率 >0.1%

**優先級**: P2

---

#### NF-12：第三方 API 版本升級協調 — MEDIUM

**發現**: Ch14 定義第三方整合標準含 Webhook 重試和降級策略。但未定義 GP 或 PSP 進行 API 版本升級時的協調流程。行業中 GP API v1 → v2 遷移通常有 90 天過渡期，但若平台未及時更新 Adapter，可能導致交易中斷。

**建議**: Ch14 新增 API 版本管理:
1. 供應商須提供 ≥ 90 天 API 版本遷移通知
2. 平台維護每個供應商的 API 版本兼容清單
3. 自動化測試套件在供應商新版本發布後 7 天內執行回歸測試
4. 雙版本並行期: 至少 30 天同時支援新舊 API

**優先級**: P2
