# 第 10 章：基礎設施需求

---

## 10.1 模組概述

基礎設施需求定義平台的非功能性要求，包括可用性 (SLA)、災難恢復 (DR)、效能目標、容量規劃。這些指標是所有技術實作的設計約束。

**核心職責**: SLA 三級體系、DR 三級體系、效能目標、容量規劃、成本模型

## 10.4 DR 三級體系

| 層級 | 適用系統 | RPO | RTO | 備註 |
|------|---------|-----|-----|------|
| **Tier 1** | 支付/錢包 | < 5 分鐘 (近零) | < 15 分鐘 | 資金安全最高優先 |
| **Tier 2** | 玩家服務/遊戲 | < 1 小時 | < 4 小時 | 客戶體驗 |
| **Tier 3** | 分析/報表 | < 24 小時 | < 24 小時 | 可容忍延遲 |

### DR 測試

| 項目 | 規則 |
|------|------|
| 演練頻率 | 每季度一次 |
| 演練範圍 | 至少覆蓋 Tier 1 系統 |
| 恢復驗證 | 演練後須驗證數據完整性 |
| 報告 | 演練結果報告提交管理層 |

### DR 演練排程與驗證標準

| 季度 | 演練範圍 | 演練類型 | 驗證標準 |
|------|---------|---------|---------|
| Q1 | Tier 1 (支付/錢包) | 完整 Failover | RTO < 15 分鐘達成 + 餘額一致性 100% + 零交易遺失 |
| Q2 | Tier 1 + Tier 2 (玩家/遊戲) | 完整 Failover | Tier 1 + 玩家服務 RTO < 4 小時 + Session 恢復率 > 99% |
| Q3 | Tier 1 (支付/錢包) | 桌面推演 + 部分 Failover | 操作手冊完整性驗證 + 新團隊成員參與 |
| Q4 | 全系統 (Tier 1+2+3) | 完整 Failover | 年度全系統驗證，含報表恢復、合規數據完整性 |

**驗證檢查清單 (每次演練必驗)**:

| 驗證項目 | 通過標準 |
|---------|---------|
| RTO 達成 | 各 Tier 恢復時間 ≤ 目標值 |
| RPO 達成 | 數據遺失量 ≤ 目標值 |
| 餘額一致性 | 恢復後錢包餘額與備份一致 (差異 = 0) |
| 交易連續性 | 恢復後所有 in-flight 交易有明確狀態 (成功/回滾) |
| 外部服務重連 | PSP、GP 連線在 RTO 內恢復 |
| 監控恢復 | 告警系統、儀表板正常運作 |
| 通知執行 | 相關人員收到通知 (時間戳記錄) |

**演練失敗處置**: 若任何 Tier 1 驗證項未通過，須在 2 週內安排補充演練，並提交根因分析報告至 CTO。

## 10.10 多租戶時區規範

| 場景 | 時區規則 |
|------|---------|
| 數據存儲 | 一律 **UTC** — 所有數據庫時間戳存為 UTC |
| 報表展示 | 依角色所屬租戶的本地時區顯示 |
| 紅利到期計算 | 依活動定義的時區（預設 UTC+8）|
| 日結/月結基準 | 依租戶配置的結算時區（預設 UTC+8 03:00）|
| API 時間格式 | ISO 8601 + 時區偏移（如 `2026-03-24T03:00:00+08:00`）|
| 跨時區報表對帳 | 轉換為 UTC 後比對 |

## 10.11 CAP 定理取捨策略

| 系統 | 策略 | 說明 |
|------|------|------|
| 錢包 / 支付 | **CP (一致性優先)** | 資金操作不容許不一致，分區時拒絕寫入並回傳錯誤 |
| 遊戲大廳 / CMS | **AP (可用性優先)** | 允許短暫的數據不一致（如遊戲列表延遲更新），確保玩家可瀏覽 |
| 風控引擎 | **CP (一致性優先)** | 規則評估需準確，分區時寧可延遲也不漏判 |
| 報表 / 分析 | **AP (可用性優先)** | 最終一致性即可，允許短暫延遲 |
| 客服系統 | **AP (可用性優先)** | 玩家能聯繫客服比即時數據一致更重要 |
