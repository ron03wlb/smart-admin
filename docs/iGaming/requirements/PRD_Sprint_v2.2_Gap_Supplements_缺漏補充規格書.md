## 執行摘要 (Executive Summary)

本規格書補充 Sprint v2.2 計畫中的十四項重要缺漏，涵蓋風險管理、合規性、安全性與營運韌性。這些項目分為三類：

1. **關鍵風險缺漏** (GAP-1 至 GAP-10): 出金流水驗證、代理帳戶安全、結算門檻、推薦人 KYC、資料駐留、可負擔性評估、GAMSTOP 匹配、報表修正、假日出金、支付方提供商破產保護

2. **術語與定義統一** (N-02): ValidBet 術語標準化

3. **新章節與配置項** (F-04, F-05): FX 風險分攤矩陣、事件回應與營運韌性完整章節

所有項目已按優先級排序（P0/P1），其中部分項目待 Ron 確認或外部團隊（合規、法務、安全）輸入。

## GAP-1: Ch2 出金流水驗證時序定義 (Priority: P0)

### 問題陳述 (Problem Statement)

Chapter 5 (Wagering Requirements) 指出「出金時觸發流水檢查」，但未定義確切時序：系統是否同步阻塞出金請求並等待流水計算完成？或將其隊列化並稍後驗證？此模糊性可能導致競態條件，玩家可在流水驗證前完成出金。

此外，如果流水服務不可用或超時，系統應如何行為？自動批准出金（潛在風險）或拒絕？

### 需求規格 (Requirements)

**P0 級要求**:

1. **同步阻塞檢查**: 出金請求到達時，系統必須：
   - 立即鎖定出金金額（預留狀態）
   - 同步查詢流水進度，SLA < 200ms
   - 若流水未完成 → 拒絕出金並顯示清晰訊息，包含剩餘流水金額和進度百分比
   - 若流水已完成 → 進入出金流程 (Ch3)

2. **超時容錯**: 若流水服務不可用（超時 > 500ms）：
   - 不得自動批准出金
   - 將請求隊列至人工審核隊列
   - 向玩家通知「出金審核中，我們的團隊將在24小時內處理」
   - 自動升級至客服主管（SLA 4 小時內人工覆核）

3. **邊界條件**:
   - 提款前 24 小時內若有新的流水計算更新 → 重新計算後再驗證
   - 部分流水（自動計算的 Valid Bets）完成，但手動審核仍pending → 接受該部分並允許等比例出金
   - 若玩家未登入超過 30 天，後續流水計算到期 → 自動標記為已完成（不應無限期卡住）

### 使用者故事 (User Stories)

1. 玩家發起出金請求，系統即時驗證流水；若未完成，清晰顯示剩餘流水金額和預估完成時間
2. 玩家在流水服務故障期間發起出金，系統隊列此請求，玩家收到「審核中」通知，不會自動批准
3. 風控人員在流水審核隊列中優先處理超時出金請求

### 驗收標準 (Acceptance Criteria)

- [ ] 出金驗證延遲可測量，99% 的驗證請求在 < 200ms 內完成
- [ ] 當流水未完成時，拒絕訊息顯示具體剩餘金額和進度百分比
- [ ] 流水服務超時情況下，出金請求自動進入人工審核隊列（無自動批准）
- [ ] 審核隊列 UI 顯示所有超時出金，按時間排序，標記風險等級
- [ ] 流水驗證邏輯在單元測試中覆蓋所有邊界條件（100% 覆蓋）
- [ ] 端對端測試驗證流水完成/未完成/超時的三種場景

### 成功指標 (Success Metrics)

- 因流水驗證失敗而被拒絕的出金比例 < 0.5%（表明檢查邏輯正確且使用者充分理解流水要求）
- 出金驗證平均延遲 < 100ms（核心 P0 指標）
- 流水超時事件 < 0.1%（服務可靠性）
- 玩家因流水驗證被拒後的申訴率 < 2%（表明通訊清晰度）

## GAP-2: Ch8 代理帳戶 MFA/IP 安全需求 (Priority: P1)

### 問題陳述 (Problem Statement)

Chapter 8 (Agents & Referrals) 定義了代理帳戶與資金結算，但未要求專門的安全控制。代理處理大量資金（信用額度分配、結算批准），應至少達到 Ch7 (Admin Security) 的相同標準。當前代理帳戶易被冒用，可能導致未經授權的資金轉移。

### 需求規格 (Requirements)

**P1 級要求**:

1. **MFA 強制**: 所有代理帳戶必須啟用 MFA
   - 支援方式: TOTP (Time-based One-Time Password) 或硬體金鑰 (FIDO2/U2F)
   - 不接受 SMS OTP（已知易被攔截）
   - 註冊時強制設置，未設置則無法登入

2. **IP 白名單**:
   - 代理只能從預先註冊的 IP 地址登入（最多 5 個 IP 地址）
   - 試圖從非白名單 IP 登入 → 在白名單驗證後允許登入（二次驗證）
   - 動態 IP 支援: 允許指定 IP 範圍（如 /24 子網）

3. **會話超時**:
   - 閒置 30 分鐘 → 自動登出
   - 確保定期重新認證敏感操作

4. **登入失敗防護**:
   - 5 次登入失敗 → 帳戶鎖定 15 分鐘
   - 上級代理收到鎖定通知（使用已註冊的通訊方式）
   - 鎖定後的登入嘗試記錄供審計用

5. **敏感操作重新認證**:
   - 信用額度調整 (> $1,000) → 重新輸入 MFA
   - 結算批准 (> $10,000) → 重新輸入 MFA
   - 代理帳戶停用/刪除 → 上級代理或管理員二次確認

6. **審計日誌**:
   - 所有代理操作記錄: 操作類型、IP 地址、設備指紋、時間戳、操作詳情
   - 日誌不可更改，至少保留 7 年
   - 敏感操作（資金轉移）額外標記為「高風險」

### 使用者故事 (User Stories)

1. 代理首次登入時強制設置 TOTP，掃描二維碼後輸入驗證碼
2. 代理從新 IP 地址登入，系統要求 IP 白名單驗證（臨時 OTP），驗證後可添加至白名單或拒絕
3. 代理進行高額信用調整，系統要求重新驗證 MFA 後才能確認
4. 合規人員查閱某代理的完整操作審計日誌，包含所有資金交易和登入事件

### 驗收標準 (Acceptance Criteria)

- [ ] 代理帳戶建立時強制設置 MFA；未設置則無法完成註冊流程
- [ ] MFA 驗證失敗後自動鎖定 15 分鐘；鎖定期間所有登入嘗試失敗
- [ ] IP 白名單驗證生效；來自非白名單 IP 的登入被拒或要求二次驗證
- [ ] 敏感操作（>$1,000 信用調整、>$10,000 結算）需重新 MFA 驗證
- [ ] 審計日誌完整記錄所有操作，不可編輯或刪除
- [ ] 端對端測試覆蓋所有 MFA 場景、IP 白名單驗證、敏感操作重新認證

### 成功指標 (Success Metrics)

- 代理帳戶未授權登入事件 = 0（基於 IP 白名單和 MFA 防護）
- MFA 設置率 = 100%（強制要求）
- 敏感操作的審計覆蓋率 = 100%
- 代理與上級代理之間的安全事件升級響應時間 < 30 分鐘

## GAP-3: Ch8 大額結算審批門檻量化 (Priority: P1)

### 問題陳述 (Problem Statement)

Chapter 8 §8.5 要求「經理批准大額結算」，但未定義「大額」的量化標準。此模糊性導致審批流程不一致，風險管理無法量化。同時，不同品牌和司法管轄區可能有不同的風險容忍度，需要可配置的門檻。

### 需求規格 (Requirements)

**P1 級要求** (📋 建議預設值，待 Ron 確認):

1. **結算審批門檻分層**:
   - **$10,000 - $49,999**: 代理經理批准（經理級）
   - **$50,000 - $99,999**: CFO 批准（財務長級）
   - **$100,000+**: CFO + CEO 雙重批准（最高級審批）
   - **月度累計 ≥ $500,000/代理**: 風險升級審查（合規團隊）

2. **可配置性**:
   - 每個品牌、司法管轄區可定制審批門檻
   - 配置存儲在 `approval_thresholds` 表，記錄變更歷史
   - 配置變更需要 CEO 或合規主管批准

3. **審批流程**:
   - 待批准結算進入隊列，按優先級排序（金額從高到低）
   - 審批人於 24 小時內決定（批准/拒絕/要求補充資訊）
   - 審批人無法在 24 小時內決定 → 自動升級至上一級審批人
   - 所有批准/拒絕決定記錄原因和審批人簽名

4. **邊界條件**:
   - 多筆結算合併至單筆，超過門檻 → 按合併後金額應用最高門檻
   - 異常結算模式偵測（如同一代理短時間內多筆 >$100,000 結算） → 自動標記為「風險」，強制最高級審批
   - 拒絕後的結算重新提交 → 需要補充文件和上級代理書面說明

### 使用者故事 (User Stories)

1. 代理提交 $75,000 結算請求，系統自動路由至 CFO 批准隊列，CFO 在系統中審核並批准/拒絕
2. 代理提交 $120,000 結算，系統要求 CFO 和 CEO 雙重批准；CFO 先批准，系統自動發送至 CEO；CEO 可於 12 小時內批准
3. 風控系統偵測到某代理本月已累計 $480,000 結算，新請求 $50,000 將超過 $500,000 月度限制 → 自動標記為「超月度限制」，觸發風險升級審查
4. 合規人員查閱結算審批歷史報告，按品牌、司法管轄區、金額範圍篩選

### 驗收標準 (Acceptance Criteria)

- [ ] 結算金額自動映射至正確的審批級別（單元測試覆蓋所有門檻邊界）
- [ ] 審批隊列 UI 按優先級排序，顯示結算金額、代理、提交時間、審批期限
- [ ] 審批人可在 UI 中批准/拒絕，輸入原因（必填）
- [ ] 超過 24 小時無審批的結算自動升級至上一級，升級事件記錄
- [ ] 審批配置界面允許管理員按品牌/司法管轄區定制門檻
- [ ] 月度累計邏輯正確計算，異常結算模式偵測生效
- [ ] 審批歷史完整保存，支援審計和報告生成

### 成功指標 (Success Metrics)

- 平均審批完成時間 < 8 小時（應低於 24 小時 SLA）
- 審批拒絕率 < 5%（過高表明門檻設置不當）
- 異常結算偵測率 > 95%（應捕捉所有高風險結算）
- 審批配置變更影響的結算準確率 = 100%

## GAP-4: Ch5 推薦人 KYC 驗證要求 (Priority: P1)

### 問題陳述 (Problem Statement)

Chapter 5 定義推薦人獎勵在被推薦人首次存款時支付，但未要求推薦人完成 KYC。此缺陷使推薦欺詐成為可能（虛構帳戶收集推薦獎勵）。此外，未偵測同一個體多個帳戶或虛假推薦關係（相同設備、IP、支付方式）。

### 需求規格 (Requirements)

**P1 級要求**:

1. **推薦人 KYC 前置條件**:
   - 推薦人必須完成 KYC Level 1+ 才能收取推薦獎勵
   - 獎勵支付前自動驗證推薦人 KYC 狀態
   - 若推薦人 KYC 未完成或待驗證 → 獎勵暫存，KYC 完成後 48 小時內支付
   - 推薦人 KYC 被拒絕或帳戶被禁用 → 獎勵不支付，返還至被推薦人帳戶

2. **推薦人與被推薦人欺詐偵測**:
   - 禁止相同設備指紋（檢查 User-Agent、屏幕解析度、瀏覽器插件等）
   - 禁止相同 IP 地址（允許 ISP 動態 IP 的同一區域但需額外驗證）
   - 禁止共享支付方式（相同銀行帳戶、信用卡或電子錢包）
   - 若偵測到上述關聯 → 標記為「可疑推薦」，自動升級至風控審核

3. **推薦人上限控制**:
   - 單個推薦人，30 天內最多 10 個成功推薦（達到首次存款條件）
   - 超過上限的推薦被標記為「異常」，風控審核後決定是否計算獎勵
   - 如推薦人月內被凍結，該月所有推薦關係重新評估

4. **獎勵回收 (Clawback)**:
   - 若被推薦人帳戶在 90 天內因欺詐被凍結，推薦人獎勵自動回收
   - 回收操作記錄，包括原因、時間、被推薦人帳戶 ID
   - 推薦人帳戶若因為多次欺詐推薦被凍結，過去 180 天內的所有獎勵回收

5. **邊界條件**:
   - 推薦人完成 KYC 後、推薦獎勵支付前，若推薦人 KYC 被拒 → 獎勵不支付，向推薦人和被推薦人通知
   - 被推薦人首次存款後退款 → 推薦獎勵仍然發放（已滿足首次存款條件），但若被推薦人帳戶最終被禁用，獎勵回收

### 使用者故事 (User Stories)

1. 玩家 A（推薦人）邀請玩家 B（被推薦人），B 首次存款；系統驗證 A 的 KYC 狀態，A 已完成 KYC → 獎勵立即支付
2. 玩家 C（推薦人）邀請玩家 D（被推薦人）；系統偵測 C 和 D 共享相同設備指紋 → 自動標記為「可疑推薦」，獎勵暫存，風控審核
3. 玩家 E 在 30 天內成功推薦 12 個帳戶（超過 10 人上限），系統標記後 3 個推薦為「異常」，風控審核是否計算獎勵
4. 被推薦人 F 在存款 45 天後因欺詐被凍結，系統自動回收推薦人 G 的獎勵，G 收到通知說明原因
5. 合規人員查閱推薦欺詐報告，篩選所有被標記為「可疑推薦」的案例

### 驗收標準 (Acceptance Criteria)

- [ ] 推薦獎勵支付前自動驗證推薦人 KYC 狀態；KYC 不完整則暫存獎勵
- [ ] 設備指紋、IP、支付方式欺詐偵測覆蓋所有相關字段，誤報率 < 2%
- [ ] 推薦人上限控制邏輯正確，30 天滾動窗口計算準確
- [ ] 獎勵回收自動執行，90 天內任何欺詐凍結都觸發回收
- [ ] 被凍結帳戶的推薦關係重新評估完成；多次欺詐推薦人的 180 天獎勵全部回收
- [ ] 端對端測試覆蓋正常推薦、可疑推薦、回收等所有場景

### 成功指標 (Success Metrics)

- 推薦欺詐率 < 1%（相比行業平均 3-5%）
- 推薦人 KYC 完成率 > 95%（鼓勵合規行為）
- 可疑推薦的人工審核完成率 > 95%（風控有效性）
- 不正當獎勵支付率 < 0.1%（控制成本損耗）
- 推薦人平均成功推薦數 6-8（低於上限 10，表明上限合理）

## GAP-5: Ch14 第三方資料駐留合規 (Priority: P1)

### 問題陳述 (Problem Statement)

歐洲平台使用基於美國的支付服務提供商 (PSP) 和 KYC 驗證服務，可能違反 GDPR 資料轉移規定。歐盟個人資料必須遵守資料駐留要求，跨境轉移須有適當的法律框架（如標準契約條款 SCC）和資料處理協議 (DPA)。第三方合作夥伴的資料處理實踐缺乏年度審計。

⏳ **本項目需合規與法務團隊輸入**

### 需求規格 (Requirements)

**P1 級要求** (規格骨架，待法務審核):

1. **資料駐留原則**:
   - EU 居民的所有 PII（個人身份識別資訊）必須存儲在 EU 資料中心
   - 第三方（PSP、KYC 提供商）処理的 PII 必須保留在資料駐留區域内
   - 臨時日誌、快取、備份也必須遵循資料駐留要求

2. **標準契約條款 (SCC) 要求**:
   - 任何跨境資料轉移（EU ↔ 美國或其他司法管轄區）必須通過 SCC 受保護
   - SCC 簽署前進行資料轉移風險評估
   - 定期審查 SCC 適用性（至少年度），應對司法管轄區變更（如美國 Executive Orders）

3. **資料處理協議 (DPA) 要求**:
   - 與所有第三方服務提供商簽署 DPA，明確定義：
     - 資料處理方式和目的
     - 資料安全措施
     - 子承包商使用規限
     - 玩家資料查取和刪除權利
   - DPA 納入服務合約附件，對雙方有約束力

4. **年度第三方審計**:
   - 所有主要資料處理第三方（年度轉移 > 10 萬筆資料）進行年度安全與合規審計
   - 審計應涵蓋: 資訊安全措施、存儲地點、存取控制、事件響應能力
   - 審計報告提交至合規部門，重大發現立即升級
   - 如審計發現違規，30 天內提出改正計畫

5. **玩家權利實現**:
   - 玩家有權存取其個人資料（GDPR 第 15 條）
   - 玩家有權更正不準確資料（GDPR 第 16 條）

## GAP-6: Ch15 可負擔性評估超時處理 (Priority: P1)

### 問題陳述 (Problem Statement)

Chapter 15 (Responsible Gaming) 定義玩家可負擔性評估（如 affordability assessment）必須在 7 天內完成，超時則 suspend deposits。但未定義若超時時玩家正在進行遊戲時的行為：系統是否應中斷進行中的遊戲？玩家是否可提取現有餘額？此模糊性可能導致玩家資金被鎖定或遊戲被強制中斷的負面體驗。

### 需求規格 (Requirements)

**P1 級要求**:

1. **進行中遊戲保護**:
   - 若評估超時時玩家正在進行中的遊戲回合 → **允許當前回合自然完成**，不得強制中斷
   - 回合完成後（無論輸贏）→ 防止新下注，顯示「可負擔性評估待完成」訊息
   - 玩家在等待評估期間不得開始新回合

2. **現有餘額提取權**:
   - 評估暫停期間，玩家仍可提取現有錢包餘額（保護玩家資金）
   - 提取不解除評估暫停（玩家仍需完成評估才能繼續遊戲）
   - 若玩家提取全額 → 帳戶自動停用，直到評估完成並已充值

3. **帳戶功能可用性**:
   - 允許玩家查看帳戶歷史、交易記錄
   - 允許玩家聯繫客服
   - 允許玩家查看餘額和可提取金額
   - 禁止: 存款、下注、進入遊戲

4. **暫停期間獎勵流水計時**:
   - 若玩家有待完成的獎勵流水（bonus wagering），在評估暫停期間暫停流水計時器
   - 評估完成或玩家提供必要資訊 → 立即恢復計時
   - 目的: 避免玩家因評估延遲而被迫放棄獎勵

5. **評估完成或資訊提供流程**:
   - 玩家完成評估問卷或提供所需文件 → 評估自動重新提交風控審核
   - 風控應在 4 小時內完成審查（SLA）
   - 審查完成或 4 小時超過 → 自動恢復玩家存款和遊戲權限
   - 若需進一步資訊 → 向玩家發送清晰的請求訊息

6. **邊界條件**:
   - 評估超時但玩家未登入 30 天 → 自動標記評估為「過期」，玩家重新登入時提示重新進行
   - 玩家在等待評估期間被觸發其他風控措施（如 GAMSTOP）→ 評估自動標記為「已解決」（帳戶已禁用）
   - 評估期間帳戶餘額變動（提取/存款嘗試/獎勵）→ 詳細記錄所有變動，供後續審計

## GAP-7: Ch15 GAMSTOP 匹配超時預設行為 (Priority: P1)

### 問題陳述 (Problem Statement)

Chapter 15 定義當 GAMSTOP 返回 ≥70% 相似度匹配時，系統對該帳戶進行 24 小時暫停以進行人工審查。但如果人工審查在 24 小時內未完成，系統的預設行為未定義：是否自動解除暫停（可能允許自我排除帳戶使用，法律風險極高）或保持暫停？此模糊性違反監管責任。

### 需求規格 (Requirements)

**P1 級要求**:

1. **預設行為: 維持暫停 (MAINTAIN HOLD)**:
   - 當 GAMSTOP 匹配的 24 小時審查期到期時，若人工審查未完成 → **不得自動解除暫停**
   - 暫停狀態保持，直到合規人員主動完成審查並決定結果
   - 自動解除暫停嚴格禁止（監管風險過高）

2. **分級升級機制**:
   - **24 小時未審查**: 自動升級至合規經理，發送警報訊息（含帳戶詳情、匹配詳情、待審查時間）
   - **48 小時未審查**: 自動升級至 MLRO (Money Laundering Reporting Officer)，帳戶自動暫停（即使原計畫解除也暫停），發送警報
   - **72 小時未審查**: 自動升級至監管合規主任，可能觸發監管機構報告（如 UK UKGC）

3. **人工審查流程**:
   - 合規人員在 GAMSTOP 控制面板中審查匹配詳情（相似度分數、匹配字段、相似帳戶清單）
   - 審查決定: 確認匹配 (confirm) / 誤報 (false positive)
   - 決定記錄: 審查人員簽名、決定原因、審查時間
   - 若決定為「確認匹配」→ 帳戶永久禁用並報告至 GAMSTOP

4. **SLA 與報告目標**:
   - **95% 的 GAMSTOP 審查應在 24 小時內完成**（目標，須監控達成率）
   - 未達 SLA 的審查列為「超期」，定期報告至管理層
   - 未達 SLA 的審查原因分析（人員不足、流程瓶頸等）

5. **邊界條件**:
   - GAMSTOP 服務故障（無法查詢匹配狀態） → 帳戶自動維持暫停，等待服務恢復；故障期間不計入 SLA
   - 帳戶同時被其他風控措施標記（如可疑交易） → GAMSTOP 審查優先，其他審查暫時延遲
   - 玩家在暫停期間申訴 → 申訴自動升級至合規經理，加速審查

6. **通信與玩家通知**:
   - GAMSTOP 匹配時，玩家收到自動通知：「您的帳戶已根據自我排除數據庫進行檢查，審查中，請待期間內聯繫客服」
   - 如審查決定為禁用 → 禁用前通知玩家，解釋原因（GAMSTOP 匹配），提供申訴途徑
   - 如審查決定為誤報 → 向玩家解釋，帳戶恢復，不記錄任何風控標記

### 使用者故事 (User Stories)

1. 帳戶 ACC-001 觸發 GAMSTOP 匹配（75% 相似度），系統暫停帳戶進行人工審查，發送通知至合規隊列
2. 48 小時後人工審查仍未開始，系統自動升級至 MLRO，發送警報，帳戶維持暫停（不自動解除）
3. 合規經理在 GAMSTOP 控制面板審查 ACC-001，確認匹配無誤，決定禁用帳戶，簽名確認
4. 系統將禁用決定報告至 GAMSTOP，向玩家發送最終禁用通知
5. 另一帳戶 ACC-002 觸發 GAMSTOP 匹配（72% 相似度），但合規經理確定為誤報（同名不同人），帳戶恢復，向玩家解釋

## GAP-8: Ch9 報表修正對已提交監管報告影響 (Priority: P1)

### 問題陳述 (Problem Statement)

Chapter 9 (Reporting & Analytics) §9.8 定義資料修正流程，允許平台更正已記錄的交易或玩家資訊，但未定義修正後的資料是否影響已提交的監管報告（如月度交易報告、玩家活動統計）。如果修正後的資料使已提交報告變得不準確，平台可能違反監管要求。修正的實質性（materiality）如何判斷？修正是否需要向監管機構報告？

⏳ **本項目需合規團隊確認**

### 需求規格 (Requirements)

**P1 級要求** (規格骨架，待合規審核):

1. **自動標記系統**:
   - 當資料修正涉及已提交的監管報告中的字段時，自動標記該修正為「影響報告」
   - 受影響的報告 ID、字段、原值、修正值、修正人員、修正時間、修正原因 → 全部記錄至 `corrections_audit_log` 表
   - 標記觸發自動通知合規部門審查

2. **實質性門檻判斷**:
   - **修正金額 ≤ 報告值的 0.1%** → 記錄為「非實質性」，僅日誌記錄，無需監管通知
   - **修正金額 > 報告值的 0.1%** → 標記為「實質性」，必須生成修正通知，評估是否向監管機構報告
   - 實質性計算示例：若原報告中玩家總存款 $1,000,000，修正 > $1,000 → 實質性

3. **修正通知生成**:
   - 實質性修正時，系統自動生成「修正通知」(Correction Notice)，包含：
     - 原始報告 ID 和提交日期
     - 修正字段、原值、修正值
     - 修正原因（如「重複交易」「輸入錯誤」「系統故障」）
     - 修正影響的報告項目（如 GGR、player acquisition 等）
     - 修正人員和日期
   - 通知格式符合監管機構要求（如 UKGC、MGA 格式）

4. **監管機構報告流程**:
   - 實質性修正自動提交至合規部門待審流程
   - 合規部門在 2 個營業日內確認修正是否需報告至監管機構
   - 若確認需報告 → 生成監管報告版本，在修正後 5 個營業日內提交至相應監管機構
   - 報告決定記錄，包括決定原因、審批人員

5. **已提交報告的版本管理**:
   - 每份提交至監管機構的報告保留不可更改的「官方版本」快照
   - 修正後如需提交修訂版本 (Amended Report)，須保持與原版本的版本控制關係
   - 修訂版本中清晰標記修正位置（如加粗、變色），便於監管機構識別

6. **特殊場景**:
   - 若已提交報告中的修正涉及多個監管報告（月度報告中的某玩家，同時涉及年度報告） → 所有受影響報告標記並評估
   - 若修正涉及新興風險（如突發的玩家欺詐發現） → 優先提交至監管機構（不等待實質性門檻）

## GAP-9: Ch3 假日期間出金 SLA 調整 (Priority: P1)

### 問題陳述 (Problem Statement)

Chapter 3 定義銀行轉賬出金的 SLA（如 1-2 個工作日），但銀行在公眾假日期間暫停業務。平台在全年 365 天運營，但無定義在假日期間出金 SLA 如何調整。例如，玩家在聖誕節前發起出金，銀行在假日期間不處理，SLA 應如何計算？系統是否應自動提示玩家選擇替代方式（如電子錢包）？

### 需求規格 (Requirements)

**P1 級要求**:

1. **假日日曆維護**:
   - 維護按國家和地區的銀行假日日曆（如英國假日、馬耳他假日、菲律賓假日等）
   - 日曆包含公眾假日和銀行特定關閉日（如額外的特別假日）
   - 年度自動更新（每年 1 月 1 日前更新下一年日曆）
   - 支援臨時假日添加（如特殊關閉公告）

2. **自動 SLA 調整**:
   - 系統自動偵測出金申請的日期
   - 若出金方式為銀行轉賬，檢查目標銀行國家的假日日曆
   - 若申請日期或 SLA 期間包含非銀行營業日，自動調整 SLA
   - **調整邏輯**: 標準 SLA + 假日天數（排除非銀行營業日，包含假日的延遲）
   - 示例：標準 SLA 1 個工作日，若玩家週五申請，下週一、二是假日，則 SLA 自動延長至週三

3. **玩家通知機制**:
   - 當系統偵測到假日影響時，向玩家自動發送通知：
     - 「您的出金正在處理。由於 [假日名稱]，銀行處理將於 [下一營業日] 恢復。預計到帳日期: [調整後 SLA 日期]。」
   - 通知應在出金申請確認時發送，清晰表明假日影響和新的預計日期
   - 通知應可在帳戶儀表板中查看

## GAP-10: Ch4 GP 破產時玩家餘額保護 (Priority: P1)

### 問題陳述 (Problem Statement)

Chapter 4 (Game Provider Integration) 定義與遊戲提供商 (GP) 的信用機制和結算流程，但未定義如果 GP 宣佈破產或無法償還結算金額，玩家的未結算賭注和帳戶餘額如何保護。在網路遊戲業中，GP 破產可導致玩家資金損失，引發監管制裁。此缺陷違反玩家資金保護的基本責任。

⏳ **本項目需法務團隊確認**

### 需求規格 (Requirements)

**P1 級要求** (規格骨架，待法務審核):

1. **未結算賭注自動回滾**:
   - 當 GP 宣佈破產或進入清算程序時，系統自動回滾所有該 GP 的 OPEN 遊戲回合
   - 回滾操作: 退款所有已下注金額至玩家原始帳戶
   - 回滾不視為「輸」，而是「投注取消」，玩家資金完全恢復
   - 回滾範圍: 所有未決議的遊戲回合（不影響已結算的遊戲）
   - 自動發送通知至受影響玩家，說明回滾原因和金額

2. **已結算但未支付的勝利金**:
   - 若 GP 欠平台已結算的玩家勝利金（Win balance），平台吸收虧損
   - **玩家優先保護原則**: 玩家勝利金必須全額支付，即使 GP 無法償還
   - 平台通過以下方式籌集資金：
     - 從該 GP 的現有信用 (Credit) 餘額抵扣
     - 若信用不足，從 GP 的委託金（如有）扣除
     - 若仍不足，平台自行承擔虧損

3. **信用機制與託管考慮**:
   - 對於前 5 大 GP（按月度遊戲額排序），考慮要求託管金（Escrow Deposits）
   - 託管金: GP 需在第三方信託帳戶存放一定比例的未結算金額（建議 10-20%），以應對破產風險
   - 託管金要求應在 GP 簽訂合約時明確，並定期審視

4. **玩家通信與支援**:
   - GP 破產公告時，玩家在 2 小時內收到自動通知
   - 通知內容:
     - 事實: [GP 名稱] 已宣佈破產/清算
     - 影響: 所有未結算遊戲將被回滾和退款
     - 行動: 「您的帳戶將在 [時間] 更新，已下注資金自動恢復。如有疑問，請聯繫客服。」
   - 專用客服頻道: 受影響玩家可優先聯繫客服，快速審理退款問題
   - SLA: 客服應在 4 小時內回應所有 GP 破產相關的玩家查詢

5. **遊戲移除與可用性**:
   - GP 破產後，平台立即禁用該 GP 的所有遊戲
   - 遊戲列表中顯示「暫時不可用」(Temporarily Unavailable) 而非刪除（便於未來恢復或玩家歷史查詢）
   - 玩家無法發起新遊戲會話，但可查看歷史遊戲記錄

6. **監管機構報告**:
   - GP 破產事件必須在 24 小時內報告至所有適用的監管機構（UKGC、MGA 等）
   - 報告內容: GP 名稱、破產公告日期、受影響玩家數、回滾金額、平台承擔虧損金額
   - 報告目的: 確保監管機構瞭解平台已採取玩家保護措施

7. **邊界條件**:
   - GP 部分破產（只有某些遊戲受影響） → 只回滾受影響遊戲，其他遊戲正常運營
   - GP 臨時服務中斷 vs. 破產 → 區分流程；臨時中斷無需自動回滾，應等待服務恢復
   - 玩家在破產期間進行新存款 → 新存款保護，但用戶不應能開始新遊戲會話
   - 已完全結算的 GP 遊戲（無未結算回合） → 無需回滾，但仍禁用新遊戲發起

8. **公司間結算流程調整**:
   - 破產前的 GP 已欠平台金額（Credit balance > 0） → 破產清算程序中優先清償
   - 破產後新生成的玩家贏利（如回滾後玩家回到 Win 狀態） → 不再結算，直接返還玩家

### 使用者故事 (User Stories)

1. GP "DragonGames" 宣佈破產，系統自動偵測，在 2 小時內向所有 DragonGames 玩家發送破產通知
2. 玩家 A 有 $200 的未結算 DragonGames 賭注，系統自動回滾，$200 恢復至玩家帳戶，玩家收到「投注回滾」的交易確認
3. DragonGames 欠平台 $50,000 的玩家勝利金，平台吸收該虧損，所有受影響玩家的勝利金全額支付
4. 合規人員在 24 小時內向 UKGC 和 MGA 報告 DragonGames 破產，包含受影響玩家數（3,500）和總回滾金額（$2.3M）
5. 玩家 B 聯繫客服咨詢破產影響，客服在優先隊列中快速回應（SLA 4 小時），解釋回滾流程和帳戶状況

### 驗收標準 (Acceptance Criteria)

- [ ] GP 破產的自動偵測機制實現（手動觸發或 API 集成），觸發後自動回滾所有未結算回合
- [ ] 回滾邏輯正確，金額計算準確，玩家帳戶恢復 = 破產前帳戶 - 已結算提款

## F-04: FX 風險分攤矩陣 (Priority: P1)

### 問題陳述 (Problem Statement)

平台支援多貨幣操作（美元、歐元、英鎊、菲律賓披索、加密貨幣等），但 FX 匯率波動的風險分攤責任未明確定義。在 Chapter 2 (Wallet)、Chapter 3 (Payment Processing)、Chapter 8 (Agent Settlement) 中，多個地方涉及貨幣轉換，但誰承擔 FX 風險（平台 vs. 玩家 vs. 代理）未清晰定義。此模糊性可能導致收益或虧損分配的爭議。

📋 **建議預設值，待 Ron 確認**

### 需求規格 (Requirements)

**P1 級要求** (建議預設值):

1. **法幣 (Fiat) 貨幣 FX 風險分攤**:
   - **匯率波動 ≤ 0.5%**: 平台吸收（不調整玩家金額或費用）
   - **匯率波動 > 0.5%**: 平台和玩家各分擔 50%
     - 示例：$100 USD → EUR 轉換，匯率波動 0.8%（> 0.5% 閾值）
     - 平台吸收 0.5%，玩家吸收 0.3%，轉換後金額 = 100 * (1 - 0.003) = €99.70
   - 玩家在轉換時明確看到 FX 波動調整，不得隱藏

2. **加密貨幣 (Crypto) 貨幣 FX 風險分攤**:
   - **匯率波動 ≤ 2%**: 平台吸收（不調整玩家金額）
   - **匯率波動 > 2%**: 玩家承擔全部（鑑於加密貨幣高波動性和玩家應有意識）
     - 玩家在轉換或充提時需重新確認匯率（覆核 UI）
     - 確認 UI 顯示實時匯率、波動幅度、預期接收金額

3. **代理結算 FX 風險**:
   - 代理結算使用「結算日匯率」(Settlement Day Rate)
   - **風險承擔**: 代理承擔從投注配置日到結算日之間的 FX 風險
   - 邏輯：投注時的匯率與結算時的匯率不同，代理應承擔該差異（鼓勵及時結算）
   - 示例：代理在 USD 時期投注 $1,000（EUR 匯率 0.92），結算時（1 週後）匯率 0.95
     - 結算金額 = 1,000 * 0.95 = €950（不是基於投注時的 0.92）
     - 代理得益於匯率改善

4. **匯率鎖定窗口** (已在 Ch2 §2.13 定義，於此重申):
   - 存款: 15 分鐘的匯率鎖定窗口（玩家確認後 15 分鐘內匯率不變）
   - 提款: 15 分鐘的匯率鎖定窗口
   - 超過鎖定窗口 → 匯率重新計算，玩家需重新確認

5. **FX P&L 報告**:
   - 每日 FX 收益/虧損報告，按貨幣對和品牌分組
   - 報告欄位：
     - 貨幣對（如 USD/EUR、USD/BTC）
     - 日期
     - 轉換量（總投注或提款額度）
     - 匯率變動百分比
     - 平台吸收的 FX 損失 (若有)
     - 玩家吸收的 FX 調整 (若有)
   - 財務團隊每月審核報告，評估 FX 策略是否合理
   - CEO/CFO 可在商業智能儀表板中查詢 FX P&L 趨勢

6. **邊界條件**:
   - 若匯率波動 > 5%（異常） → 系統自動標記為「異常波動」，加強審計和確認流程
   - 若平台因 FX 虧損超過月度預算 > 10% → 自動升級至 CFO 審查（可能調整分攤策略）
   - 加密貨幣匯率來自多個 oracle，若 oracle 不一致 → 使用加權平均或中位數

### 使用者故事 (User Stories)

1. 玩家 A（美國）充 $100 USD，轉換為 EUR，實時匯率 0.92，但 15 分鐘後波動至 0.91；玩家在鎖定窗口內確認 → 接收 €92
2. 玩家 B 在大匯率波動期間（0.8%） 轉換 $10,000 USD → EUR；系統顯示匯率波動 0.8%（> 0.5% 閾值），玩家吸收 0.3% 損失
3. 代理 C 用 $50,000 USD 投注，匯率 0.93；一週後匯率升至 0.96 時結算；代理結算金額 = 50,000 * 0.96 = €48,000（受益）
4. 玩家 D 轉換加密貨幣 BTC → USD，波動 2.5% > 2% 閾值；系統顯示風險提醒，要求玩家重新確認最終金額
5. 財務團隊每月查閱 FX P&L 報告，看到 USD/EUR 對的 FX 虧損 $5,000，評估是否調整分攤策略

### 驗收標準 (Acceptance Criteria)

- [ ] FX 風險分攤邏輯實現：法幣 ≤0.5% 平台吸收，加密 ≤2% 平台吸收

| **P1 - 嚴重** | 核心功能不可用，可用性 < 99.9%，或重大風險 | 50% 以上玩家或特定國家完全癱瘓 | 遊戲平台不可用、提款系統故障、重大安全漏洞 |
| **P2 - 中等** | 功能部分受限，可用性 95-99.9%，風險可控 | 小於 50% 玩家或特定功能受限 | 某遊戲提供商故障、報告功能故障、輕度安全問題 |
| **P3 - 輕微** | 體驗略受影響但功能正常，可用性 > 99.9% | 少數玩家或非關鍵功能 | UI 顯示異常、部分統計報告延遲、測試環境問題 |
| **P4 - 微不足道** | 幾乎無影響，僅通知和跟進 | 無實質影響 | 美化工作、文檔更新、內部流程改進 |

#### 分級決策樹

```
事件發生
  ↓
系統/服務完全不可用？
  ├─ 是，玩家資金/資料風險？
  │   ├─ 是 → P0
  │   └─ 否 → 評估影響 → P0/P1
  └─ 否
      ↓
      可用性 < 99.9% 或重大功能故障？
      ├─ 是 → P1
      └─ 否
          ↓
          影響 > 1,000 玩家或特定功能受限？
          ├─ 是 → P2
          └─ 否
              ↓
              影響 < 100 玩家或非關鍵功能？
              ├─ 是 → P3
              └─ 否 → P4
```

### 16.2 戰情室激活標準 (War Room Activation Criteria)

#### 何時激活

**自動激活**:
- **P0 事件**: 自動激活，無需人工確認
- **P1 事件**: 自動激活（如事件影響玩家、支付、安全）

**可選激活**:
- **P2 事件**: 若持續超過 30 分鐘未解決，可考慮激活
- **P3 事件**: 一般不激活，但可設立臨時 Slack 頻道協調

#### 戰情室構成

| 角色 | 責任 | 參與條件 |
|-----|------|---------|
| **事件指揮** (Incident Commander) | 統籌回應、決策、通信 | P0/P1 事件必須 |
| **技術負責人** | 技術診斷和修復 | P0/P1 必須 |
| **營運負責人** | 玩家通知、支援協調 | P0/P1 必須 |
| **合規負責人** | 監管通知評估 | P0/P1（若涉及監管）必須 |
| **財務負責人** | 成本評估、保險通知 | P0（若涉及重大損失）必須 |
| **CEO/CFO** | 決策級審批 | P0 必須；P1 可選 |

#### 戰情室工具

- **即時通信**: Slack #incident-response（或專用頻道，每級別一個）
- **共享文檔**: Google Doc 即時事件日誌，記錄時間線、決策、行動
- **語音會議**: Zoom/Google Meet，每 15-30 分鐘召開一次狀態更新
- **儀表板**: 實時系統狀態監控儀表板（CPU、記憶體、延遲、錯誤率）

### 16.5 事件後分析 (Post-Mortem Requirements)

#### 何時進行

- **P0 事件**: 強制，必須在 72 小時內召開初步會議
- **P1 事件**: 強制，必須在 5 個工作日內召開
- **P2 事件**: 可選，但建議進行（至少簡要分析）
- **P3 及以下**: 通常不進行正式分析，但可記錄日誌

#### 事件後分析會議議程

1. **時間線** (15 分鐘)
   - 事件檢測時間
   - 首次通知時間
   - 各關鍵決策時間點
   - 解決時間
   - 視覺化時間線圖表

2. **根本原因分析 (RCA)** (30 分鐘)
   - 直接原因 (Direct Cause)
   - 根本原因 (Root Cause)
   - 贡献因素 (Contributing Factors)
   - 使用 5 Why 或 Fishbone 圖表

3. **影響評估** (10 分鐘)
   - 受影響玩家數
   - 資料影響（若有）
   - 財務影響（停機損失、補償成本）
   - 監管或品牌影響

4. **改進行動** (30 分鐘)
   - 短期行動 (1 週內): 快速修復臨時問題
   - 中期行動 (1 個月內): 永久修復或改進
   - 長期行動 (3 個月以上): 架構或流程改進
   - 每個行動指派擁有者和期限

5. **結論與經驗教訓** (10 分鐘)
   - 做得好的地方（讚揚）
   - 改進空間
   - 預防措施（防止類似事件）

#### 事件後分析文檔格式

```markdown
# 事件後分析: INC-2026-03-25-001

## 執行摘要
[1-2 段落總結事件、影響、根本原因和關鍵改進]

## 事件詳情
- **檢測時間**: [時間]
- **解決時間**: [時間]
- **總持續時間**: [時間長度]
- **嚴重等級**: P0
- **根本原因**: [簡述]

## 時間線
[分鐘級詳細時間線，包括發現、通知、診斷、解決步驟]

## 根本原因分析
[詳細 RCA，使用 5 Why 或因果圖]

## 影響
- 受影響玩家: [數字]
- 停機時間損失: $[數字]
- 補償成本: $[數字]
- 監管報告: [是/否，若是列出報告內容]

## 改進行動

| 行動 | 類別 | 擁有者 | 期限 | 狀態 |
|-----|------|--------|------|------|
| [行動描述] | 短期/中期/長期 | [名字] | [日期] | 進行中/待啟動 |

## 經驗教訣
- 做得好: [正面經驗]
- 改進空間: [可改進項]
- 預防措施: [防止類似事件的措施]

## 參與者
[列出參與響應的人員和角色]

## 核准
[由 CTO/CEO 簽署，確認分析完整]
```

### 16.7 業務連續性計畫 (Business Continuity Plan, BCP) 概覽

#### 目的

確保平台在重大中斷（自然災害、重大安全事件、提供商故障等）時能夠快速恢復，最小化業務中斷和玩家影響。

#### 範圍

涵蓋所有關鍵業務功能和系統：
- 遊戲平台（玩家登入、遊戲播放、支付）
- 支付系統（存款、提款）
- 客服和支援
- 報告和合規系統
- 管理員控制台

#### 關鍵指標

- **RTO (Recovery Time Objective)** - P0 事件: 1 小時；P1 事件: 4 小時
- **RPO (Recovery Point Objective)** - < 5 分鐘的資料損失（使用連續複製）

#### 備份策略

- **地理分佈**: 主資料中心 + 備份資料中心（至少 100 公里距離）
- **複製**: 關鍵資料庫進行實時同步複製（RPO < 1 分鐘）
- **備份頻率**: 每小時完整備份 + 每分鐘增量備份
- **備份驗證**: 每週進行恢復測試，確保備份可用

#### 故障轉移流程

```
監控系統偵測到主資料中心故障
  ↓
自動或手動啟動故障轉移
  ↓
DNS/負載均衡器轉移至備份資料中心
  ↓
備份系統接管：
  - 玩家會話恢復
  - 資料庫同步確認
  - 第三方服務重新連接（PSP、KYC 等）
  ↓
驗證系統健康狀況
  ↓
通知玩家和監管機構
  ↓
監控恢復品質和性能
```

#### BCP 文檔維護

- **文檔位置**: [內部wiki或文檔管理系統]
- **擁有者**: CTO 或技術主管
- **審核頻率**: 每季度審核，確保聯繫資訊和流程最新
- **版本管理**: 保留所有版本歷史，標記生效日期

### 16.8 災難恢復演練 (Disaster Recovery Drills)

#### 演練頻率

- **全面 DR 演練**: 每季度（Q1, Q2, Q3, Q4）進行一次，模擬資料中心故障，驗證完整故障轉移
- **部分演練**: 每月進行一次，測試特定組件（如資料庫備份恢復、PSP 故障轉移等）
- **台式演練** (Tabletop): 每半年進行一次，模擬各種災難場景（如勒索軟體攻擊、供應商破產），評估響應計畫

#### 演練計畫與執行

##### 全面 DR 演練

```
時間表:
- T-2 周: 公告演練，通知所有相關團隊
- T-1 周: 預檢，確認測試環境準備完畢
- 演練日:
  - 關閉主資料中心（測試環境）
  - 啟動故障轉移至備份中心
  - 驗證所有系統功能（登入、遊戲、支付等）
  - 測試玩家通知系統
  - 監控性能指標（延遲、錯誤率）
  - 記錄所有問題和改進
- T+1 周: 召開演練回顧會議，討論發現和改進行動
- T+4 周: 完成所有改進行動並驗證修復
```

##### 部分演練

```
示例: 資料庫故障轉移演練

- 選擇備用資料庫副本進行測試
- 啟動恢復流程，將應用程序指向恢復的資料庫
- 驗證資料一致性和應用功能
- 測試自動故障轉移邏輯（監控系統如何偵測故障並自動轉移）
- 記錄 RTO（多久完成轉移）和 RPO（資料損失量）
```

##### 台式演練

```
場景範例: 勒索軟體攻擊

參與者: 技術、安全、法務、合規、CEO
流程:
1. 簡報場景: 勒索軟體已感染主資料庫
2. 時間壓力: 2 小時內決策（付贖金？恢復備份？）
3. 討論:
   - 如何檢測和隔離被感染系統？
   - 如何驗證備份未被感染？
   - 玩家和監管機構通知計畫？
   - 保險和法律含義？
4. 記錄決策和延遲可能發生的原因
```

#### 演練文檔與報告

每次演練後生成演練報告，包括：

```markdown
# DR 演練報告: [演練名稱] - [日期]

- **類型**: 全面/部分/台式
- **場景**: [模擬的災難]

| 目標 | 預期結果 | 實際結果 | 通過/失敗 |

## 主要發現
- [發現 1]
- [發現 2]
- [改進機會]

## 改進行動
| 行動 | 優先級 | 擁有者 | 期限 |
|-----|--------|--------|------|
| [行動] | P0/P1/P2 | [名字] | [日期] |

[簡述演練成果和整體準備狀況]
```

## 附錄 A：術語與定義

### 本規格書中使用的關鍵術語

| 術語 | 定義 |
|-----|------|
| **validBet** | 已驗證且計入流水要求的投注金額。SSOT（Single Source of Truth）術語。過時變體：ValidTurnover、ValidSpins。 |
| **Wagering Progress** | 玩家達成流水要求的進度百分比。計算: (validBet / wagering_requirement) × 100% |
| **War Room** | 在重大事件期間召集的協調團隊和即時通信頻道，用於快速決策和升級 |
| **RTO (Recovery Time Objective)** | 系統在災難後應恢復至可運營狀態的目標時間 |
| **RPO (Recovery Point Objective)** | 系統可接受的最大資料損失時間視窗 |
| **MTTR (Mean Time To Repair)** | 從事件偵測到解決的平均時間 |
| **SLA (Service Level Agreement)** | 平台對系統可用性和性能的承諾 |
| **P0/P1/P2/P3/P4** | 事件嚴重程度等級，P0 最嚴重，P4 最輕微 |
