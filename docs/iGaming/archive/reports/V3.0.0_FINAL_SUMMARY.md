## 關鍵技術決策

### 1. 為何選擇完全移除代碼實作？

**理由**：
- 文檔定位轉變：實作指南 → 架構設計文檔
- 避免代碼與文檔不同步問題
- 提升可讀性（代碼區塊佔用大量空間）
- 專注業務邏輯和架構設計

**保留內容**：
- ✅ Mermaid 流程圖（清晰的視覺化）
- ✅ 配置矩陣（表格形式，易於維護）
- ✅ 業務規則描述（Markdown 文本）
- ✅ ASCII 架構圖（文本繪圖）

**效果**：
- 平均文件大小減少 43.6%
- 核心內容更聚焦
- 維護成本降低

### 2. 為何 Seamless Wallet 保持 14 個獨立文件？

**理由**：
- 每個專題自成體系（Token 驗證、冪等性設計、流水計算等）
- 合併為單一文件會產生 8000+ 行巨型文件，難以維護
- `00_INDEX.md` 提供 P0/P1 優先級導航，解決發現性問題
- 移至財務中心下建立邏輯關聯（Seamless Wallet 是錢包模型的延伸）

**效果**：
- 每個專題獨立可讀（平均 600 行）
- 清晰的優先級分類（P0 必讀 vs P1 進階）
- 與財務中心模塊邏輯一致

### 3. 為何使用 `git mv` 而非直接移動？

**理由**：
- 保留完整的 Git 歷史（文件追溯能力）
- 支援 `git log --follow` 追蹤文件移動
- 符合 Git 最佳實踐

**效果**：
- 100% Git 歷史可追溯
- 所有文件移動完整記錄
- 支援回滾和歷史查詢

### 4. 為何選擇增量遷移（6 階段）而非一次性？

**理由**：
- 每階段獨立驗證，降低風險
- 可隨時暫停或調整策略
- Git 歷史清晰（每階段獨立提交）
- 適合生產環境，不影響現有文檔使用

**效果**：
- 6 個獨立 Git commit（可獨立回滾）
- 每階段完整的驗證報告
- 清晰的執行進度追蹤

### 5. 為何交叉引用覆蓋率目標設為 80%？

**理由**：
- 80/20 法則：80% 覆蓋率能解決大部分導航問題
- 部分文檔（如遷移指南、報告）不需要交叉引用
- 平衡維護成本與收益

**實際達成**：
- Phase 4 後：95.7%
- Phase 6 最終：98.5%
- 超越目標 +18.5 百分點
