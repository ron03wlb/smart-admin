# 日均過億投注與取款對帳系統：完整架構設計指南

**業務背景**：iGame 多商戶博弈平台，30M 註冊用戶，100+ 遊戲商戶/渠道，日均交易量 1~2 億筆。技術棧：PostgreSQL + Citus + Kafka + Redis + Flink + Spring Boot。

**設計目標**：零資金損失、分鐘級差異發現、小時級 T+1 全量對帳、完整審計軌跡。

---

## 一、系統全域架構總覽

### 1.1 對帳系統在平台中的定位

對帳系統不是一個獨立的「工具」，而是**資金安全的最後一道防線**。它處於交易鏈路的下游，以**觀察者**角色消費各系統的交易事件，交叉驗證資金流轉的正確性。

```
┌──────────────────────────────────────────────────────────────────────┐
│                        iGame 多商戶博弈平台                           │
├──────────┬──────────┬──────────┬──────────┬──────────────────────────┤
│  投注系統  │  結算系統  │  錢包系統  │  支付系統  │  100+ 遊戲商戶 API      │
│  (Bet)    │ (Settle) │ (Wallet) │ (Payment)│  (Game Providers)       │
└────┬─────┴────┬─────┴────┬─────┴────┬─────┴────────┬───────────────┘
     │          │          │          │              │
     ▼          ▼          ▼          ▼              ▼
┌──────────────────────────────────────────────────────────────────────┐
│                    Kafka 交易事件總線                                  │
│  topic: bet-events, settle-events, wallet-events, payment-events    │
└────────────────────────────┬─────────────────────────────────────────┘
                             │
                             ▼
┌──────────────────────────────────────────────────────────────────────┐
│                      對帳系統（Reconciliation）                       │
│  ┌─────────────┐  ┌──────────────┐  ┌─────────────┐  ┌───────────┐ │
│  │ 準實時對帳    │  │ T+1 批量對帳  │  │ 商戶結算對帳  │  │ 差異處理   │ │
│  │ (Flink)     │  │ (Flink Batch)│  │ (Scheduled) │  │ 與調帳中心  │ │
│  └─────────────┘  └──────────────┘  └─────────────┘  └───────────┘ │
└──────────────────────────────────────────────────────────────────────┘
```

### 1.2 四層對帳架構

| 層級 | 名稱 | 時效 | 目的 | 對帳對象 |
|------|------|------|------|---------|
| **L1** | 準實時對帳 | 秒~分鐘級 | 即時發現高風險異常 | 投注流水 vs 錢包變動 |
| **L2** | T+1 內部全量對帳 | 小時級 | 系統性核對所有交易 | 投注 ↔ 結算 ↔ 錢包 三方交叉 |
| **L3** | 渠道對帳 | T+1~T+2 | 與 100+ 商戶帳單比對 | 平台記錄 vs 商戶帳單 |
| **L4** | 商戶結算對帳 | 週/月 | 分潤佣金結算核算 | 平台帳務 vs 商戶應結金額 |

## 二、核心資料模型設計

### 2.1 統一交易流水模型（Transaction Ledger）

這是對帳的「黃金基準」——所有交易最終都映射到這張統一流水表。

```sql
-- 統一交易流水表（Citus 分布式表，以 user_id 為分片鍵）
CREATE TABLE transaction_ledger (
    -- 主鍵與標識
    id                  BIGINT GENERATED ALWAYS AS IDENTITY,
    txn_id              VARCHAR(64) NOT NULL,          -- 全局唯一交易ID
    idempotency_key     VARCHAR(128) NOT NULL,         -- 冪等鍵
    
    -- 業務維度
    user_id             BIGINT NOT NULL,               -- 用戶ID（Citus 分片鍵）
    merchant_id         INTEGER NOT NULL,              -- 遊戲商戶ID
    txn_type            SMALLINT NOT NULL,             -- 1:投注 2:派獎 3:充值 4:取款 5:紅利 6:退款 7:調帳
    wallet_type         SMALLINT NOT NULL DEFAULT 1,   -- 1:現金錢包 2:紅利錢包 3:凍結錢包
    
    -- 金額（使用 BIGINT 存儲「分」，避免浮點精度問題）
    amount              BIGINT NOT NULL,               -- 交易金額（分）正數=入帳，負數=出帳
    balance_before      BIGINT NOT NULL,               -- 交易前餘額
    balance_after       BIGINT NOT NULL,               -- 交易後餘額
    currency            CHAR(3) NOT NULL DEFAULT 'CNY',-- 幣種 ISO 4217
    
    -- 關聯標識
    bet_id              VARCHAR(64),                   -- 投注單號（投注/派獎場景）
    round_id            VARCHAR(64),                   -- 遊戲局號
    payment_order_id    VARCHAR(64),                   -- 支付訂單號（充值/取款場景）
    settle_id           VARCHAR(64),                   -- 結算批次號
    
    -- 狀態與時間
    status              SMALLINT NOT NULL DEFAULT 1,   -- 1:待處理 2:成功 3:失敗 4:沖正
    created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    settled_at          TIMESTAMPTZ,                   -- 結算確認時間
    
    -- 對帳標記
    recon_status        SMALLINT NOT NULL DEFAULT 0,   -- 0:未對帳 1:已匹配 2:差異 3:已處理
    recon_batch_id      VARCHAR(32),                   -- 對帳批次號
    recon_at            TIMESTAMPTZ,                   -- 對帳時間
    
    -- 約束
    PRIMARY KEY (user_id, id),
    CONSTRAINT uk_txn_idempotency UNIQUE (idempotency_key)
);

-- Citus 分片
SELECT create_distributed_table('transaction_ledger', 'user_id');

-- 對帳查詢索引
CREATE INDEX idx_ledger_recon ON transaction_ledger (recon_status, created_at) 
    WHERE recon_status = 0;
CREATE INDEX idx_ledger_merchant_date ON transaction_ledger (merchant_id, created_at);
CREATE INDEX idx_ledger_txn_id ON transaction_ledger (txn_id);
CREATE INDEX idx_ledger_bet_id ON transaction_ledger (bet_id) WHERE bet_id IS NOT NULL;
```

**設計決策解析**：

- **金額用 BIGINT 存「分」而非 DECIMAL**：避免浮點運算精度問題，`123.45 元` 存為 `12345`。在日均過億的場景下，DECIMAL 的運算開銷顯著高於 BIGINT。
- **以 user_id 作為 Citus 分片鍵**：投注是最高頻操作，同一用戶的交易天然關聯，co-located query 可避免跨分片 JOIN。
- **recon_status 冗餘欄位**：空間換時間，T+1 對帳時直接掃描 `recon_status=0` 的記錄，避免全表掃描。
- **balance_before / balance_after**：記錄餘額快照，使得對帳時不需要回溯計算，直接校驗 `前餘額 + 交易金額 = 後餘額`。

## 三、L1 準實時對帳引擎（Flink Streaming）

### 3.1 設計目標

準實時對帳不追求全量覆蓋，而是聚焦**高風險場景的快速發現**：

- 投注扣款但錢包未變動（掉單）
- 同一筆投注被重複扣款（重入）
- 餘額連續性斷裂（`balance_after_prev ≠ balance_before_curr`）
- 異常大額交易（超過歷史 P99 閾值）

### 3.2 Flink 流處理拓撲

```
                        ┌─────────────────┐
bet-events ──────────▶  │                 │
                        │   Interval Join  │──▶ matched-stream ──▶ 驗證邏輯 ──▶ 正常/差異
wallet-events ───────▶  │  (60s window)   │
                        │                 │──▶ unmatched-stream ──▶ 延遲重試 ──▶ 告警
                        └─────────────────┘
                        
settle-events ───────▶  ┌─────────────────┐
                        │  Balance Chain   │──▶ 餘額連續性 ──▶ 斷裂告警
wallet-events ───────▶  │  Validator       │
                        └─────────────────┘
```

### 3.3 核心處理邏輯

**Step 1：雙流 Interval Join（投注 vs 錢包）**

```java
// Flink 雙流 Join：投注事件 與 錢包變動事件
// 以 bet_id 作為 Join Key，時間窗口 60 秒
@Component
public class BetWalletReconJob {

    public void buildPipeline(StreamExecutionEnvironment env) {
        
        // 來源流 A：投注事件
        DataStream<BetEvent> betStream = env
            .addSource(new FlinkKafkaConsumer<>("bet-events", 
                new BetEventDeserializer(), kafkaProps))
            .assignTimestampsAndWatermarks(
                WatermarkStrategy.<BetEvent>forBoundedOutOfOrderness(Duration.ofSeconds(10))
                    .withTimestampAssigner((event, ts) -> event.getCreatedAt()))
            .keyBy(BetEvent::getBetId);
        
        // 來源流 B：錢包變動事件
        DataStream<WalletEvent> walletStream = env
            .addSource(new FlinkKafkaConsumer<>("wallet-events", 
                new WalletEventDeserializer(), kafkaProps))
            .assignTimestampsAndWatermarks(
                WatermarkStrategy.<WalletEvent>forBoundedOutOfOrderness(Duration.ofSeconds(10))
                    .withTimestampAssigner((event, ts) -> event.getCreatedAt()))
            .filter(e -> e.getRefType() == RefType.BET)  // 只關注投注相關的錢包變動
            .keyBy(WalletEvent::getRefId);
        
        // Interval Join：投注事件發生後 60 秒內，錢包應有對應變動
        betStream.intervalJoin(walletStream)
            .between(Time.seconds(-5), Time.seconds(60))  // 錢包可能比投注早5秒（預扣）
            .process(new BetWalletJoinFunction())
            .name("bet-wallet-interval-join");
    }
}

public class BetWalletJoinFunction 
    extends ProcessJoinFunction<BetEvent, WalletEvent, ReconResult> {
    
    @Override
    public void processElement(BetEvent bet, WalletEvent wallet, Context ctx, 
                                Collector<ReconResult> out) {
        ReconResult result = new ReconResult();
        result.setBetId(bet.getBetId());
        result.setUserId(bet.getUserId());
        
        // 校驗 1：金額一致性
        if (Math.abs(bet.getAmount()) != Math.abs(wallet.getAmount())) {
            result.setStatus(ReconStatus.AMOUNT_MISMATCH);
            result.setAmountDiff(bet.getAmount() - wallet.getAmount());
        }
        // 校驗 2：方向一致性（投注應為出帳）
        else if (bet.getBetType() == BetType.PLACE_BET 
                 && wallet.getDirection() != Direction.DEBIT) {
            result.setStatus(ReconStatus.DIRECTION_MISMATCH);
        }
        // 校驗 3：餘額連續性
        else if (wallet.getBalanceBefore() + wallet.getAmount() != wallet.getBalanceAfter()) {
            result.setStatus(ReconStatus.BALANCE_BREAK);
        }
        else {
            result.setStatus(ReconStatus.MATCHED);
        }
        
        out.collect(result);
    }
}
```

**Step 2：未匹配事件的側輸出處理**

```java
// 投注事件超過 60 秒仍未匹配到錢包變動 → 可能掉單
public class UnmatchedBetDetector extends KeyedProcessFunction<String, BetEvent, Alert> {
    
    private ValueState<BetEvent> pendingBet;
    
    @Override
    public void open(Configuration parameters) {
        ValueStateDescriptor<BetEvent> desc = 
            new ValueStateDescriptor<>("pending-bet", BetEvent.class);
        // 設定 State TTL，避免狀態無限膨脹
        StateTtlConfig ttlConfig = StateTtlConfig.newBuilder(Time.minutes(10))
            .setUpdateType(StateTtlConfig.UpdateType.OnCreateAndWrite)
            .cleanupFullSnapshot()
            .build();
        desc.enableTimeToLive(ttlConfig);
        pendingBet = getRuntimeContext().getState(desc);
    }
    
    @Override
    public void processElement(BetEvent event, Context ctx, Collector<Alert> out) 
        throws Exception {
        pendingBet.update(event);
        // 註冊 60 秒後的定時器
        ctx.timerService().registerEventTimeTimer(
            event.getCreatedAt() + Duration.ofSeconds(60).toMillis());
    }
    
    @Override
    public void onTimer(long timestamp, OnTimerContext ctx, Collector<Alert> out) 
        throws Exception {
        BetEvent bet = pendingBet.value();
        if (bet != null) {
            // 60 秒內未被清除 → 錢包未響應
            out.collect(Alert.builder()
                .level(AlertLevel.CRITICAL)
                .type("BET_NO_WALLET_RESPONSE")
                .message(String.format("投注 %s 用戶 %d 金額 %d 無對應錢包變動", 
                    bet.getBetId(), bet.getUserId(), bet.getAmount()))
                .build());
            pendingBet.clear();
        }
    }
}
```

**Step 3：餘額連續性校驗**

```java
// 按用戶分組，驗證錢包流水的餘額是否連續
// 上一筆的 balance_after 應等於下一筆的 balance_before
public class BalanceChainValidator 
    extends KeyedProcessFunction<Long, WalletEvent, BalanceBreakAlert> {
    
    // 按 (user_id, wallet_type) 維護上一筆餘額
    private MapState<Integer, Long> lastBalanceByWalletType;
    
    @Override
    public void processElement(WalletEvent event, Context ctx, 
                                Collector<BalanceBreakAlert> out) throws Exception {
        Integer walletType = event.getWalletType();
        Long lastBalance = lastBalanceByWalletType.get(walletType);
        
        if (lastBalance != null && !lastBalance.equals(event.getBalanceBefore())) {
            out.collect(BalanceBreakAlert.builder()
                .userId(event.getUserId())
                .walletType(walletType)
                .expectedBalance(lastBalance)
                .actualBalanceBefore(event.getBalanceBefore())
                .txnId(event.getWalletTxnId())
                .gap(event.getBalanceBefore() - lastBalance)
                .build());
        }
        
        lastBalanceByWalletType.put(walletType, event.getBalanceAfter());
    }
}
```

## 四、L2 T+1 內部全量對帳引擎

### 4.1 為什麼不能只靠準實時？

準實時對帳有三個天然盲區：

1. **Kafka 消費延遲或 Rebalance**：事件可能被延遲處理，超出 Join 窗口
2. **Flink Checkpoint 失敗回滾**：可能導致部分事件被跳過
3. **資料庫與 Kafka 的不一致**：業務系統可能 DB 提交成功但 Kafka 發送失敗（非事務消息場景）

因此 T+1 全量對帳是**兜底機制**，以資料庫中的持久化數據為準。

### 4.3 Flink Batch 比對核心邏輯

```java
/**
 * T+1 全量對帳核心：三方交叉比對
 * 
 * 性能目標：1 億筆交易在 2 小時內完成
 * 
 * 策略：
 * 1. 按 user_id 分區（與 Citus 分片對齊），確保同一用戶的數據在同一 TaskManager
 * 2. Sort-Merge Join 而非 Hash Join（記憶體可控）
 * 3. 分批寫入差異結果，避免大事務
 */
public class T1ReconBatchJob {
    
    public void execute(ExecutionEnvironment env, LocalDate reconDate) {
        
        String batchId = String.format("RECON-INTERNAL-%s-%03d", 
            reconDate.format(DateTimeFormatter.BASIC_ISO_DATE),
            getNextSeq());
        
        // Phase 1: 數據抽取（使用 JDBC 批量讀取，分片並行）
        DataSet<BetRecord> bets = env.createInput(
            JDBCInputFormat.buildJDBCInputFormat()
                .setDrivername("org.postgresql.Driver")
                .setDBUrl(citusMasterUrl)
                .setQuery("""
                    SELECT bet_id, user_id, merchant_id, bet_type, amount, 
                           payout_amount, status, created_at, merchant_txn_ref
                    FROM bet_transaction 
                    WHERE created_at >= ? AND created_at < ?
                      AND status IN (2, 4)  -- 只對帳成功和沖正的
                    """)
                .setParametersProvider(new DateRangeParams(reconDate))
                .setRowTypeInfo(betTypeInfo)
                .finish());
        
        DataSet<WalletRecord> wallets = env.createInput(/* similar JDBC source */);
        
        // Phase 2: 雙向 Full Outer Join
        DataSet<ReconPair> reconPairs = bets
            .fullOuterJoin(wallets)
            .where("betId")
            .equalTo("refId")
            .with(new ReconJoinFunction());
        
        // Phase 3: 逐筆校驗
        DataSet<ReconResult> results = reconPairs.map(new ReconValidationMapper());
        
        // Phase 4: 按結果分流
        DataSet<ReconResult> matched = results.filter(r -> r.isMatched());
        DataSet<ReconDiscrepancy> discrepancies = results
            .filter(r -> !r.isMatched())
            .map(new DiscrepancyMapper(batchId));
        
        // Phase 5: 寫入結果
        discrepancies.output(new DiscrepancyJDBCSink());
        
        // Phase 6: 彙總統計
        DataSet<ReconSummary> summary = results
            .groupBy("merchantId")
            .reduceGroup(new SummaryAggregator(batchId));
        summary.output(new SummaryJDBCSink());
    }
}

/**
 * Full Outer Join 函數：處理三種情況
 */
public class ReconJoinFunction 
    implements JoinFunction<BetRecord, WalletRecord, ReconPair> {
    
    // 匹配成功
    @Override
    public ReconPair join(BetRecord bet, WalletRecord wallet) {
        if (bet != null && wallet != null) {
            return ReconPair.matched(bet, wallet);
        } else if (bet != null) {
            return ReconPair.sourceOnly(bet);      // 長款：投注有、錢包無
        } else {
            return ReconPair.targetOnly(wallet);   // 短款：錢包有、投注無
        }
    }
}

/**
 * 校驗邏輯：逐項檢查
 */
public class ReconValidationMapper implements MapFunction<ReconPair, ReconResult> {
    
    @Override
    public ReconResult map(ReconPair pair) {
        if (pair.isSourceOnly()) {
            return ReconResult.discrepancy(DiscrepancyType.SOURCE_ONLY, Severity.CRITICAL,
                "投注記錄無對應錢包變動，疑似掉單", pair);
        }
        if (pair.isTargetOnly()) {
            return ReconResult.discrepancy(DiscrepancyType.TARGET_ONLY, Severity.CRITICAL,
                "錢包變動無對應投注記錄，疑似幽靈交易", pair);
        }
        
        BetRecord bet = pair.getBet();
        WalletRecord wallet = pair.getWallet();
        
        // 校驗 1：金額一致性
        long expectedWalletAmount = calculateExpectedWalletAmount(bet);
        if (expectedWalletAmount != wallet.getAmount()) {
            return ReconResult.discrepancy(DiscrepancyType.AMOUNT_MISMATCH, Severity.HIGH,
                String.format("金額不一致: 預期=%d, 實際=%d, 差異=%d",
                    expectedWalletAmount, wallet.getAmount(), 
                    expectedWalletAmount - wallet.getAmount()), pair);
        }
        
        // 校驗 2：狀態一致性
        if (!isStatusConsistent(bet.getStatus(), wallet.getStatus())) {
            return ReconResult.discrepancy(DiscrepancyType.STATUS_MISMATCH, Severity.HIGH,
                String.format("狀態不一致: 投注=%s, 錢包=%s", 
                    bet.getStatus(), wallet.getStatus()), pair);
        }
        
        // 校驗 3：時間合理性（錢包變動應在投注後 5 秒內）
        long timeDiff = Math.abs(
            wallet.getCreatedAt().toEpochMilli() - bet.getCreatedAt().toEpochMilli());
        if (timeDiff > 5000) {
            return ReconResult.discrepancy(DiscrepancyType.TIME_ANOMALY, Severity.LOW,
                String.format("時間偏差 %dms 超過閾值", timeDiff), pair);
        }
        
        return ReconResult.matched(pair);
    }
    
    private long calculateExpectedWalletAmount(BetRecord bet) {
        return switch (bet.getBetType()) {
            case PLACE_BET -> -bet.getAmount();          // 下注 → 錢包出帳
            case WIN       -> bet.getPayoutAmount();      // 贏 → 錢包入帳
            case LOSE      -> 0;                          // 輸 → 無錢包變動（已在下注時扣除）
            case CANCEL    -> bet.getAmount();            // 取消 → 退回錢包
            default -> throw new IllegalArgumentException("Unknown bet type: " + bet.getBetType());
        };
    }
}
```

### 4.4 餘額連續性全量校驗

這是 T+1 對帳的**殺手級校驗**——利用 PostgreSQL 窗口函數在資料庫層完成：

```sql
-- 餘額連續性校驗：找出 balance_after(上一筆) ≠ balance_before(下一筆) 的斷裂點
WITH ordered_txns AS (
    SELECT 
        user_id,
        wallet_type,
        wallet_txn_id,
        balance_before,
        balance_after,
        amount,
        created_at,
        LAG(balance_after) OVER (
            PARTITION BY user_id, wallet_type 
            ORDER BY created_at, wallet_txn_id
        ) AS prev_balance_after
    FROM wallet_transaction
    WHERE created_at >= :recon_date 
      AND created_at < :recon_date + INTERVAL '1 day'
      AND status = 2  -- 只校驗成功的
)
SELECT 
    user_id,
    wallet_type,
    wallet_txn_id,
    prev_balance_after AS expected_balance_before,
    balance_before AS actual_balance_before,
    (balance_before - prev_balance_after) AS gap,
    created_at
FROM ordered_txns
WHERE prev_balance_after IS NOT NULL 
  AND prev_balance_after != balance_before;
```

**為什麼這個校驗如此重要？** 餘額連續性斷裂意味著：

- 可能有一筆交易未被記錄（丟失流水）
- 可能有並發問題導致餘額計算錯誤（樂觀鎖失敗未正確處理）
- 可能有直接修改資料庫的非法操作（繞過應用層）

任何餘額斷裂都應視為 **P0 嚴重事件**。

### 4.5 彙總金額比對（兜底校驗）

逐筆比對完成後，再做一層彙總校驗作為 Double Check：

```sql
-- 按商戶+交易類型+幣種維度彙總
-- 投注系統的彙總
SELECT 
    merchant_id,
    bet_type,
    COUNT(*) AS txn_count,
    SUM(amount) AS total_amount,
    SUM(payout_amount) AS total_payout
FROM bet_transaction
WHERE created_at >= :recon_date AND created_at < :recon_date + INTERVAL '1 day'
  AND status = 2
GROUP BY merchant_id, bet_type;

-- 錢包系統的彙總
SELECT 
    -- 需要通過 ref_id JOIN 回 bet_transaction 取 merchant_id
    b.merchant_id,
    w.ref_type,
    COUNT(*) AS txn_count,
    SUM(w.amount) AS total_amount
FROM wallet_transaction w
JOIN bet_transaction b ON w.ref_id = b.bet_id AND w.user_id = b.user_id
WHERE w.created_at >= :recon_date AND w.created_at < :recon_date + INTERVAL '1 day'
  AND w.status = 2
GROUP BY b.merchant_id, w.ref_type;

-- 兩個結果集比對：total_amount 不一致 → 說明逐筆比對可能遺漏了某些記錄
```

```java
/**
 * 商戶帳單適配器介面
 * 每個商戶實現一個 Adapter，將異構帳單轉為統一格式
 */
public interface MerchantStatementAdapter {
    
    /** 商戶標識 */
    int getMerchantId();
    
    /** 拉取帳單（Pull 模式） */
    List<StandardStatement> fetchStatement(LocalDate date);
    
    /** 解析帳單（Push 模式，商戶推送給我們） */
    List<StandardStatement> parseStatement(byte[] rawData, String format);
    
    /** 統一格式 */
    @Data
    class StandardStatement {
        private String merchantTxnRef;     // 商戶側交易ID
        private String platformTxnRef;     // 平台側交易ID（部分商戶會回傳）
        private String txnType;            // bet/win/refund/cancel
        private long amount;               // 金額（分）
        private String currency;
        private Instant txnTime;
        private String userId;             // 用戶標識（商戶側）
        private Map<String, Object> extra; // 擴展欄位
    }
}

/**
 * 商戶帳單調度器：管理 100+ 商戶的帳單拉取
 */
@Component
public class MerchantStatementScheduler {
    
    @Autowired
    private List<MerchantStatementAdapter> adapters;  // Spring 自動注入所有實現
    
    @Autowired
    private MerchantStatementRepository repository;
    
    /**
     * 每日定時拉取帳單
     * 使用線程池並行拉取，但每個商戶有獨立的重試策略
     */
    @Scheduled(cron = "0 0 6-12 * * ?")  // 每天 6:00~12:00 每小時嘗試
    public void pullMerchantStatements() {
        LocalDate reconDate = LocalDate.now().minusDays(1);
        
        for (MerchantStatementAdapter adapter : adapters) {
            CompletableFuture.runAsync(() -> {
                try {
                    String importBatchId = generateBatchId(adapter.getMerchantId(), reconDate);
                    
                    // 冪等檢查：已導入則跳過
                    if (repository.existsByBatch(importBatchId)) {
                        log.info("商戶 {} 日期 {} 帳單已導入，跳過", 
                            adapter.getMerchantId(), reconDate);
                        return;
                    }
                    
                    List<StandardStatement> statements = adapter.fetchStatement(reconDate);
                    
                    // 批量寫入 merchant_statement 表
                    repository.batchInsert(statements, importBatchId);
                    
                    log.info("商戶 {} 帳單導入完成，共 {} 筆", 
                        adapter.getMerchantId(), statements.size());
                        
                } catch (Exception e) {
                    log.error("商戶 {} 帳單拉取失敗", adapter.getMerchantId(), e);
                    alertService.sendAlert(AlertLevel.HIGH, 
                        "商戶帳單拉取失敗: " + adapter.getMerchantId());
                }
            }, merchantStatementExecutor);
        }
    }
}
```

```sql
-- Step 1: 以平台記錄為基準的 LEFT JOIN（找長款）
SELECT 
    'PLATFORM_ONLY' AS discrepancy_type,
    b.bet_id,
    b.user_id,
    b.merchant_id,
    b.amount AS platform_amount,
    NULL AS merchant_amount,
    b.merchant_txn_ref

LEFT JOIN merchant_statement ms 
    ON b.merchant_txn_ref = ms.merchant_txn_ref 
    AND b.merchant_id = ms.merchant_id
    AND ms.statement_date = :recon_date
WHERE b.created_at >= :recon_date AND b.created_at < :recon_date + INTERVAL '1 day'
  AND b.merchant_id = :merchant_id
  AND b.status = 2
  AND ms.id IS NULL  -- 商戶帳單中無此記錄

UNION ALL

-- Step 2: 以商戶帳單為基準的 LEFT JOIN（找短款 — 更危險）
SELECT

    NULL AS user_id,
    ms.merchant_id,
    NULL AS platform_amount,
    ms.amount AS merchant_amount,
    ms.merchant_txn_ref
```

## 六、L4 商戶結算對帳

### 6.1 結算模型

```
商戶結算金額 = 用戶總投注額 - 用戶總贏額 - 平台佣金
             = 商戶總 GGR (Gross Gaming Revenue) × (1 - 佣金比例)

GGR = Total Bets - Total Wins
Net Settlement = GGR × (1 - Commission Rate)
```

### 6.2 結算對帳 SQL

```sql
-- 商戶月結算計算
WITH merchant_ggr AS (
    SELECT 
        merchant_id,
        SUM(CASE WHEN bet_type = 1 THEN amount ELSE 0 END) AS total_bets,
        SUM(CASE WHEN bet_type = 2 THEN payout_amount ELSE 0 END) AS total_wins,
        COUNT(DISTINCT user_id) AS active_users,
        COUNT(DISTINCT round_id) AS total_rounds
    FROM bet_transaction
    WHERE created_at >= :settle_period_start 
      AND created_at < :settle_period_end
      AND status = 2
    GROUP BY merchant_id
),
settlement_calc AS (
    SELECT 
        g.merchant_id,
        g.total_bets,
        g.total_wins,
        (g.total_bets - g.total_wins) AS ggr,
        mc.commission_rate,
        ROUND((g.total_bets - g.total_wins) * (1 - mc.commission_rate)) AS net_settlement,
        g.active_users,
        g.total_rounds
    FROM merchant_ggr g
    JOIN merchant_config mc ON g.merchant_id = mc.merchant_id
)
SELECT 
    s.*,
    ms.merchant_reported_ggr,
    ms.merchant_reported_settlement,
    ABS(s.ggr - ms.merchant_reported_ggr) AS ggr_diff,
    ABS(s.net_settlement - ms.merchant_reported_settlement) AS settlement_diff
FROM settlement_calc s
LEFT JOIN merchant_settlement_report ms 
    ON s.merchant_id = ms.merchant_id 
    AND ms.period_start = :settle_period_start
WHERE ABS(s.ggr - COALESCE(ms.merchant_reported_ggr, 0)) > :tolerance_amount
   OR ms.id IS NULL;
```

## 七、差異處理與調帳中心

### 7.1 差異自動處理策略

```java
/**
 * 差異分級自動處理引擎
 * 
 * 原則：
 * 1. 小額差異可自動處理，大額必須人工審核
 * 2. 自動處理也必須產生完整的審計軌跡
 * 3. 所有調帳操作必須冪等
 */
@Service
public class DiscrepancyAutoResolver {
    
    // 自動處理閾值配置
    private static final long AUTO_RESOLVE_MAX_AMOUNT = 10000;  // 100 元以下自動處理
    private static final int AUTO_RESOLVE_MAX_COUNT_PER_BATCH = 100;  // 每批次最多自動處理 100 筆
    
    @Transactional
    public void processDiscrepancies(String batchId) {
        List<ReconDiscrepancy> pending = discrepancyRepo
            .findByBatchIdAndHandleStatus(batchId, HandleStatus.PENDING);
        
        int autoCount = 0;
        
        for (ReconDiscrepancy d : pending) {
            AutoResolveDecision decision = evaluate(d);
            
            switch (decision.getAction()) {
                case AUTO_RETRY:
                    // 場景：投注成功但錢包未記錄 → 觸發補償重試
                    if (autoCount < AUTO_RESOLVE_MAX_COUNT_PER_BATCH) {
                        retryWalletDeduction(d);
                        d.setHandleStatus(HandleStatus.AUTO_RESOLVED);
                        d.setHandleType(HandleType.AUTO_RETRY);
                        autoCount++;
                    }
                    break;
                    
                case ESCALATE_TO_MANUAL:
                    // 場景：金額差異超過閾值，或短款（嚴重）
                    d.setHandleStatus(HandleStatus.MANUAL_PENDING);
                    d.setSeverity(Severity.CRITICAL);
                    alertService.notifyOps(d);
                    break;
                    
                case AUTO_IGNORE:
                    // 場景：時間戳輕微偏差，不影響資金
                    d.setHandleStatus(HandleStatus.AUTO_RESOLVED);
                    d.setHandleType(HandleType.IGNORED);
                    d.setHandleNote("時間偏差在可接受範圍內，自動忽略");
                    break;
                    
                case FREEZE_ACCOUNT:
                    // 場景：餘額連續性斷裂，疑似異常操作
                    d.setHandleStatus(HandleStatus.MANUAL_PENDING);
                    walletService.freezeWallet(d.getUserId(), "對帳異常凍結: " + d.getId());
                    alertService.notifySecurity(d);  // 通知安全團隊
                    break;
            }
            
            discrepancyRepo.save(d);
        }
    }
    
    private AutoResolveDecision evaluate(ReconDiscrepancy d) {
        // 規則引擎決策
        if (d.getDiscrepancyType() == DiscrepancyType.TARGET_ONLY) {
            return AutoResolveDecision.of(Action.FREEZE_ACCOUNT); // 短款一律凍結
        }
        if (d.getDiscrepancyType() == DiscrepancyType.BALANCE_BREAK) {
            return AutoResolveDecision.of(Action.FREEZE_ACCOUNT); // 餘額斷裂一律凍結
        }
        if (d.getDiscrepancyType() == DiscrepancyType.SOURCE_ONLY 
            && Math.abs(d.getSourceAmount()) <= AUTO_RESOLVE_MAX_AMOUNT) {
            return AutoResolveDecision.of(Action.AUTO_RETRY);     // 小額掉單自動重試
        }
        if (d.getDiscrepancyType() == DiscrepancyType.TIME_ANOMALY) {
            return AutoResolveDecision.of(Action.AUTO_IGNORE);    // 時間偏差忽略
        }
        return AutoResolveDecision.of(Action.ESCALATE_TO_MANUAL); // 其餘人工處理
    }
}
```

### 7.2 調帳操作的冪等與審計

```java
/**
 * 調帳服務
 * 
 * 核心原則：
 * 1. 調帳不是「修改」原記錄，而是產生一筆新的「沖正/補入」交易
 * 2. 使用 adjustment_id 作為冪等鍵，防止重複調帳
 * 3. 超過閾值（如 1000 元）需要二級審批
 */
@Service
public class AdjustmentService {
    
    @Transactional
    public AdjustmentResult createAdjustment(AdjustmentRequest request) {
        
        // 冪等檢查
        if (adjustmentRepo.existsByAdjustmentId(request.getAdjustmentId())) {
            return AdjustmentResult.duplicate(request.getAdjustmentId());
        }
        
        AdjustmentRecord record = AdjustmentRecord.builder()
            .adjustmentId(request.getAdjustmentId())
            .discrepancyId(request.getDiscrepancyId())
            .userId(request.getUserId())
            .adjustmentType(request.getType())      // 補入/扣回/沖正
            .amount(request.getAmount())
            .reason(request.getReason())
            .createdBy(request.getOperator())
            .build();
        
        // 金額閾值判斷
        if (Math.abs(request.getAmount()) > APPROVAL_THRESHOLD) {
            record.setApprovalStatus(ApprovalStatus.PENDING);
            return AdjustmentResult.pendingApproval(record);
        }
        
        // 小額直接執行
        record.setApprovalStatus(ApprovalStatus.AUTO_APPROVED);
        return executeAdjustment(record);
    }
    
    @Transactional
    public AdjustmentResult executeAdjustment(AdjustmentRecord record) {
        // 通過錢包系統產生一筆調帳交易
        WalletAdjustRequest walletReq = WalletAdjustRequest.builder()
            .userId(record.getUserId())
            .amount(record.getAmount())
            .txnType(TxnType.ADJUSTMENT)
            .idempotencyKey("ADJ-" + record.getAdjustmentId())  // 錢包側冪等
            .build();
        
        WalletResult walletResult = walletService.adjust(walletReq);
        
        record.setExecuteStatus(ExecuteStatus.EXECUTED);
        record.setExecuteTxnId(walletResult.getTxnId());
        record.setExecutedAt(Instant.now());
        
        adjustmentRepo.save(record);
        
        // 更新原始差異記錄狀態
        discrepancyRepo.updateHandleStatus(
            record.getDiscrepancyId(), HandleStatus.RESOLVED);
        
        return AdjustmentResult.success(record);
    }
}
```

### 8.1 對帳批次冪等

```java
/**
 * 對帳批次的冪等保證
 * 
 * 設計：batch_id = RECON-{type}-{date}-{seq}
 * 同一天同一類型的對帳，seq 遞增
 * 如果上一批次未完成（狀態=進行中），則恢復而非重新創建
 */
@Service
public class ReconBatchManager {
    
    @Transactional
    public ReconBatch getOrCreateBatch(ReconType type, LocalDate date) {
        // 查找是否有未完成的批次
        Optional<ReconBatch> existing = batchRepo
            .findByTypeAndDateAndStatus(type, date, BatchStatus.IN_PROGRESS);
        
        if (existing.isPresent()) {
            log.info("恢復未完成的對帳批次: {}", existing.get().getBatchId());
            return existing.get();
        }
        
        // 查找已完成的批次（冪等：已完成則不再執行）
        Optional<ReconBatch> completed = batchRepo
            .findByTypeAndDateAndStatus(type, date, BatchStatus.COMPLETED);
        
        if (completed.isPresent()) {
            log.info("對帳批次已完成，跳過: {}", completed.get().getBatchId());
            return completed.get();
        }
        
        // 創建新批次
        int nextSeq = batchRepo.getNextSeq(type, date);
        String batchId = String.format("RECON-%s-%s-%03d",
            type.name(), date.format(DateTimeFormatter.BASIC_ISO_DATE), nextSeq);
        
        return batchRepo.save(ReconBatch.create(batchId, type, date));
    }
}
```

### 8.2 Checkpoint 與斷點續跑

```java
/**
 * 大批量對帳的斷點續跑機制
 * 
 * 1 億筆交易不可能一個事務處理完
 * 按 user_id 區間分段處理，每段完成後記錄 checkpoint
 */
@Service
public class ReconCheckpointManager {
    
    // checkpoint 存儲在 Redis 中，格式: recon:checkpoint:{batchId} → last_user_id
    private static final String CHECKPOINT_KEY = "recon:checkpoint:%s";
    
    public void processInSegments(String batchId, ReconProcessor processor) {
        // 讀取上次 checkpoint
        Long lastProcessedUserId = getCheckpoint(batchId);
        
        // 按 user_id 區間分段（Citus 分片感知）
        List<UserIdRange> segments = calculateSegments(lastProcessedUserId);
        
        for (UserIdRange segment : segments) {
            try {
                processor.processSegment(batchId, segment);
                
                // 每段完成後更新 checkpoint
                saveCheckpoint(batchId, segment.getEndUserId());
                
            } catch (Exception e) {
                log.error("對帳段 {} 處理失敗，已保存 checkpoint 至 userId={}", 
                    segment, segment.getStartUserId());
                throw e;  // 上層捕獲後可稍後重試，從 checkpoint 恢復
            }
        }
    }
    
    private void saveCheckpoint(String batchId, Long userId) {
        redisTemplate.opsForValue().set(
            String.format(CHECKPOINT_KEY, batchId), 
            userId.toString(),
            Duration.ofDays(3));
    }
}
```

## 十一、面試高頻問題精解

### Q1：為什麼不能只做彙總金額比對？

**答**：彙總比對存在「正負相消」盲區。假設有一筆 +100 的幽靈交易（平台未記錄但商戶已結算）和一筆 -100 的掉單（平台已記錄但商戶未確認），彙總金額完全相等，但實際上有兩筆差異。逐筆明細比對是基礎，彙總比對只能作為 Double Check 的輔助手段。

### Q2：對帳系統如何保證自身的正確性？

**答**：三層保障：(1) 對帳邏輯的單元測試覆蓋率 > 95%，特別是邊界條件（跨日交易、沖正再沖正等）；(2) 定期用已知結果的測試數據集「影子對帳」，驗證系統輸出與預期一致；(3) 逐筆比對完成後，再做彙總金額校驗作為 Cross Check，兩種方法互相驗證。

### Q3：T+1 對帳期間的交易如何處理？

**答**：對帳使用**快照隔離**的思想。T+1 對帳的數據窗口是 `[T日 00:00:00, T+1日 00:00:00)`，只處理 created_at 落在此窗口的交易。對帳期間新產生的 T+1 日交易不受影響，它們會在 T+2 日的對帳批次中被處理。這本質上就是 MVCC 快照隔離在業務層面的映射——每個對帳批次看到的是一個「一致性快照」。

### Q4：100+ 商戶帳單格式各異如何維護？

**答**：使用 Adapter Pattern + 配置驅動。每個商戶一個 Adapter 類實現統一接口，帳單欄位映射通過 YAML 配置而非硬編碼。新增商戶只需新增一個 Adapter 配置文件。對於格式高度相似的商戶群（如都是同一遊戲平台聚合商），抽取 Base Adapter 減少重複。定期執行「帳單格式一致性檢測」，商戶改了格式能立即發現。

### Q5：如何處理跨日交易和時區問題？

**答**：統一使用 UTC 時間戳存儲，對帳窗口以 UTC 為基準。跨日交易（如 UTC 23:59 下注，UTC 00:01 結算）會出現投注在 T 日而結算在 T+1 日的情況。解決方案是對帳時不僅比對 T 日的投注，還要向前延伸到 T-1 日最後 N 分鐘的未匹配記錄（滑動窗口補償）。
