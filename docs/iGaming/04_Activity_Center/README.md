### 流水計算完整公式
```text
ValidTurnover = BetAmount
                × Layer1_RiskFactor     (05-01: 0 or 1)
                × Layer2_StatusFactor   (02-04: 0%, 50%, 100%)
                × Layer3_GameWeight     (04-02: 5%-100%)
```

### 核心 API 契約
- **Base Validation API**: `RiskEngine.validateTurnover()` (05-01 提供)
- **Finance Layer**: `effective_turnover_base × status_factor` (02-04)
- **Activity Layer**: `valid_turnover_finance × game_weight` (04-02)

## 架構約束與設計原則

### 架構約束
- ✅ **Layer 3 位置**: 活動系統必須依賴 Layer 1 (05-01) 風控驗證 + Layer 2 (02-04) 狀態因子計算
- ✅ **異步風控**: 流水驗證採用異步模式，避免影響遊戲即時性
- ✅ **統一事件源**: Finance 與 Activity 模組均訂閱相同的 Kafka Topic: `game.rounds.settled`

### 業務約束
- ✅ **獎金濫用佔比**: 63.8% iGaming 詐騙來自獎金濫用，風控機制必須深度整合
- ✅ **合規優先**: 歐洲市場的負責任博彩不是選項，是必要條件
- ✅ **配置驅動**: 嚴禁硬編碼活動規則，所有變數必須來自後台配置

### 數據一致性
- ✅ **每日對帳**: 凌晨 03:00 執行 Finance vs Activity 流水對帳，偏差 > 0.01% 觸發警報
- ✅ **配置集中管理**: 遊戲權重表必須存放於統一配置服務，禁止硬編碼
