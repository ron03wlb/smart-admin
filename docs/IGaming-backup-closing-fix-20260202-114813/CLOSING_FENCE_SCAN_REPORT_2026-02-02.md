**錯誤類型**: 使用語言標識符作為**閉合標記**（而非開啟標記）

❌ **錯誤模式**:
```markdown
```mermaid

```text    ← 錯誤！閉合標記不應有語言標識符

```

✅ **正確模式**:
```markdown
```mermaid
erDiagram
    PLAYER ||--|| WALLET : has
```         ← 正確！純三個反引號閉合

---
```

### 3. 檢測邏輯（成功的方法）

```bash
# 對每一行 ```language 模式：
if [[ "$line" =~ ^```(text|yaml|markdown|sql|json)[[:space:]]*$ ]]; then
    # 1. 檢查前一行是否有內容（非空）
    if [ -n "$prev_trimmed" ]; then
        # 2. 檢查後一行是否為空、分隔符或標題
        if [ -z "$next_trimmed" ] || [[ "$next_trimmed" =~ ^--- ]] || [[ "$next_trimmed" =~ ^# ]]; then
            # → 這是閉合標記錯誤！
        fi
    fi
fi
```

**關鍵邏輯**:
- 前一行有內容 → 可能是閉合標記
- 後一行為空/分隔符/標題 → 確認為閉合標記
- 開啟標記的後一行通常是代碼內容（非空）

## 🔬 根本原因分析

### 為什麼會產生這個錯誤？

#### 1. Markdown 語法誤解

**錯誤認知**:
- 開發者認為代碼塊需要"對稱"：開啟和閉合都用相同格式
- 誤以為 ` ```language` 在閉合時也需要語言標識符

**正確規範**:
```markdown
# Markdown 代碼塊語法（CommonMark 規範）
```language    ← 開啟標記（可選語言標識符）
code here
```            ← 閉合標記（永遠不帶語言標識符）
```

#### 2. IDE 自動補全誤導

某些編輯器的自動補全可能會在輸入 ` ``` ` 時自動添加語言標識符，導致開發者誤以為這是標準做法。

#### 3. 文檔模板問題

部分文檔可能基於錯誤的模板創建，導致錯誤模式在多個文件中複製。

### 為何 Mermaid 解析器更嚴格？

**Mermaid Live Editor** 的解析器比一般 Markdown 渲染器更嚴格：

| 渲染器 | 行為 | 影響 |
|-------|------|------|
| **GitHub Markdown** | 寬容模式，可能忽略某些語法錯誤 | 🟡 可能正常顯示 |
| **VS Code Preview** | 基於 markdown-it，較寬容 | 🟡 可能正常顯示 |
| **Mermaid Live Editor** | 嚴格模式，立即報錯 | 🔴 解析失敗 |
| **MkDocs/Docusaurus** | 嚴格模式（取決於配置） | 🔴 可能拒絕渲染 |

**結論**: 錯誤的閉合標記可能在某些環境下"看起來正常"，但會在嚴格的渲染器中導致解析失敗。

### 2. 上下文分析是關鍵

單純搜索 ` ```text` 模式無法區分：
- ✅ 正確的開啟標記：` ```text`（後面是代碼內容）

**必須檢查前後行才能準確判斷**。
