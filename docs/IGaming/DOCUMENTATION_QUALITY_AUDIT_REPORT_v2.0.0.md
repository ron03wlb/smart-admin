#### P2-1: 術語一致性全局替換 ⚠️ 已延後

**狀態**: Deferred（因技術複雜度高）

**失敗原因**:
- Bash 腳本全局替換導致災難性錯誤
- 所有數字 "0" 被替換為 "Bonus"（例如：2026-01-31 → 2Bonus26-Bonus1-31）
- 影響範圍：16,776 處錯誤替換
- 立即回滾：`git restore .`（零數據損失）

**教訓**:
- 全局文本替換需要使用專業工具（Python/Perl）
- 必須先小範圍測試再批量執行
- 需要更複雜的正則表達式和上下文檢測

**建議方案**:
- 使用 Python 腳本 + 正則表達式
- 實現術語邊界檢測（避免誤替換）
- 分批執行（每次 10 個文檔）
- 人工審核每批結果

**預估工作量**: 6-8 小時（需要專業開發）

### B. 關鍵技術決策

#### 決策 1: 活動系統文檔拆分策略

**背景**: 原文檔 1,447 行過長，影響可讀性

**選項**:
- 選項 A: 保持原樣（不拆分）
- 選項 B: 拆分為 2 個文檔（架構 + 業務）
- 選項 C: 拆分為 3 個文檔 + 1 個索引（推薦）✅

**決策**: 選項 C

**理由**:
1. 職責分離清晰（架構、業務邏輯、風控）
2. 單個文檔長度適中（400-600 lines）
3. 索引文檔提供清晰導航
4. 參考 seamless-wallet 成功模式

#### 決策 2: 術語一致性替換工具選擇

**背景**: 需要全局替換術語（例如：流水需求 → 流水要求）

**選項**:
- 選項 A: Bash sed/awk（失敗）❌
- 選項 B: Python + 正則表達式（推薦）✅
- 選項 C: 人工手動替換

**決策**: 選項 B（延後執行）

**理由**:
1. Bash 無法處理複雜邊界檢測
2. Python 支持正則表達式和上下文分析
3. 可實現批量執行 + 人工審核

#### 決策 3: Mermaid 圖表優化策略

**背景**: 部分圖表節點數 > 15，可讀性欠佳

**選項**:
- 選項 A: 強制拆分所有複雜圖表
- 選項 B: 保留原圖 + 創建簡化版（推薦）✅
- 選項 C: 不優化

**決策**: 選項 B（延後執行）

**理由**:
1. 原圖邏輯連貫性好，拆分可能破壞
2. 提供兩個版本供用戶選擇
3. 時間成本高，優先級較低
